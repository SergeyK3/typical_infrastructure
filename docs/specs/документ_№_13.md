# Документ №13. MVP Data Dictionary v1

## 1. Назначение документа

Этот документ фиксирует единый словарь данных для MVP-платформы. Его задача — синхронизировать терминологию и структуру данных между:

- концептуальной и логической моделью данных;
- backend entities и ORM models;
- API contracts / DTO;
- frontend forms, tables, cards и filters;
- onboarding flow;
- правилами именования полей в системе.

Документ нужен для того, чтобы одна и та же сущность не называлась по-разному в базе, API, интерфейсе и документации.

---

## 2. Что должен зафиксировать Data Dictionary

MVP Data Dictionary должен определить:

1. список ключевых сущностей MVP;
2. назначение каждой сущности;
3. canonical name сущности;
4. recommended table name / collection name;
5. canonical field set;
6. назначение каждого поля;
7. тип поля на бизнес-уровне;
8. обязательность поля;
9. допустимые значения / reference rules;
10. различие между domain field, DB column, API field и UI label;
11. audit-поля и lifecycle-поля;
12. единые naming conventions.

---

## 3. Принцип словаря данных

Для каждой сущности фиксируется четыре уровня представления:

1. **Business term** — как сущность называется на языке предметной области.
2. **Domain / backend name** — как сущность называется в сервисах и коде.
3. **Persistence name** — как она называется в БД.
4. **API / UI representation** — как она приходит в DTO и показывается на экране.

Пример:

- Business term: Клиент
- Domain name: Client
- DB table: `clients`
- API object: `client`
- UI label: «Клиент» / «Организация-клиент»

Это правило применяется ко всем сущностям MVP.

---

## 4. Границы MVP-словаря

В первую версию словаря входят сущности, которые критичны для первого рабочего контура:

- Client
- OrgUnit
- Position
- Employee
- Account
- Role
- AccountRoleAssignment
- OnboardingRun
- OnboardingTemplateSnapshot / RunItem (если используется в модели запуска)
- WizardDraft / WizardPayload (на уровне API, если мастер сохраняет промежуточное состояние)

Во вне-MVP остаются:

- детальные skill profiles;
- assessment results;
- KPI history;
- learning assignments;
- advanced notifications;
- complex permission exceptions;
- document storage metadata beyond minimum required set.

## 5. Общие правила именования

## 5.1. Общие принципы

Во всех слоях желательно придерживаться следующих правил:

- имена сущностей в singular на domain-уровне: `Client`, `Employee`, `Role`;
- имена таблиц в plural snake_case: `clients`, `employees`, `account_roles`;
- имена полей в БД — snake_case;
- имена полей в API — snake_case или camelCase, но в пределах MVP должен быть выбран один стандарт;
- имена полей в frontend state лучше делать максимально близкими к API;
- UI labels не должны влиять на технические имена.

Для снижения трения в реализации рекомендуется:

- **DB:** snake_case
- **API DTO:** snake_case
- **frontend model:** по возможности повторяет API field names

Это упрощает трассировку поля от формы до БД.

## 5.2. Идентификаторы

Рекомендуемые правила:

- первичный ключ сущности: `id` на API-уровне;
- в БД допускается `id` как primary key;
- внешние ключи: `<entity>_id`;
- публичные коды: `code`;
- человеко-читаемые названия: `name`;
- локализованные названия: `name_ru`, `name_en` — только если это действительно нужно.

## 5.3. Audit-поля

Для большинства сущностей MVP рекомендуется единый набор:

- `created_at`
- `created_by`
- `updated_at`
- `updated_by`
- `is_active`

При необходимости soft-delete:

- `deleted_at`
- `deleted_by`

Но soft-delete нужно включать только там, где оно действительно влияет на бизнес-логику.

## 6. Канонический состав сущностей MVP

## 6.1. Client

### Назначение
Юридическое лицо / организация-заказчик, внутри которой строится оргструктура и запускается onboarding.

### Canonical names

- Business term: Клиент / Компания / Юрлицо
- Domain name: `Client`
- DB table: `clients`
- API object: `client`

### Recommended fields

| Field | Назначение | Тип | Required | Notes |
|---|---|---:|---:|---|
| id | Уникальный идентификатор клиента | integer / uuid | yes | PK |
| code | Уникальный код клиента | string | yes | short stable identifier |
| name | Основное наименование | string | yes | canonical display name |
| short_name | Краткое наименование | string | no | optional |
| legal_name | Юридическое наименование | string | no | if different from display |
| tax_id | БИН / ИНН / налоговый идентификатор | string | no | jurisdiction-specific |
| status | Статус клиента | enum/string | yes | draft / active / archived |
| primary_contact_name | Контактное лицо | string | no | MVP optional |
| primary_contact_email | Email контакта | string | no | MVP optional |
| primary_contact_phone | Телефон контакта | string | no | MVP optional |
| notes | Комментарий | text | no | |
| created_at | Дата создания | datetime | yes | audit |
| updated_at | Дата обновления | datetime | yes | audit |
| is_active | Признак активности | boolean | yes | default true |

### UI labels

- `name` → «Название клиента»
- `short_name` → «Краткое название»
- `legal_name` → «Юридическое название»
- `tax_id` → «БИН/ИНН»
- `status` → «Статус»

### Notes

`code` должен быть коротким, устойчивым и пригодным для ссылок, API routes, фильтров и импорта.

## 7. Reference fields и словарные значения

Для MVP желательно заранее зафиксировать, какие поля являются:

- свободным текстом;
- контролируемым enum;
- ссылкой на справочник;
- вычисляемым значением.

### Минимально рекомендуемые enum-группы

- `client.status`
- `org_unit.unit_type`
- `employee.employment_status`
- `account.status`
- `account.auth_provider`
- `role.role_type`
- `role.scope_type`
- `onboarding_run.status`
- `onboarding_run_item.status`
- `onboarding_run_item.item_type`

### Принцип работы с enum

Для MVP лучше:

- хранить канонический код значения;
- отображать человеко-читаемую подпись в UI;
- не использовать UI label как persisted value.

Пример:

- persisted: `active`
- UI: «Активен»

## 8. Правила для API DTO

## 8.1. DTO-слои

Для каждой ключевой сущности желательно отделять:

- List Item DTO
- Detail DTO
- Create DTO
- Update DTO
- Reference DTO

Пример для Employee:

- `EmployeeListItem`
- `EmployeeDetail`
- `EmployeeCreate`
- `EmployeeUpdate`
- `EmployeeRef`

## 8.2. Поля, которые не должны попадать в Create/Update напрямую

Нельзя без явного решения пробрасывать в клиентский ввод:

- `created_at`
- `updated_at`
- `created_by`
- `updated_by`
- `password_hash`
- системные служебные флаги, не относящиеся к пользовательскому сценарию

## 8.3. Вычисляемые поля DTO

На API-уровне допустимы вычисляемые поля:

- `employee.full_name`
- `org_unit.breadcrumb`
- `position.org_unit_name`
- `account.role_codes`
- `onboarding_run.progress_percent`

Но они должны быть явно помечены как derived / read-only.

## 9. Правила для экранной модели

Словарь данных должен помогать frontend-разработке. Поэтому у каждой сущности нужно различать:

1. **Table fields** — какие поля показываются в списке;
2. **Detail fields** — какие поля показываются в карточке;
3. **Editable fields** — какие поля доступны в форме;
4. **Filter fields** — по каким полям можно искать и фильтровать;
5. **System fields** — какие поля скрыты от обычного пользователя.

### Пример: Employee

**Table fields:**

- full_name
- org_unit_id / org_unit_name
- position_id / position_name
- email
- employment_status
- is_active

**Detail fields:**

- все table fields
- employee_code
- manager_employee_id
- hire_date
- created_at
- updated_at

**Editable fields:**

- last_name
- first_name
- middle_name
- email
- phone
- org_unit_id
- position_id
- manager_employee_id
- employment_status
- hire_date

## 10. Naming rules для UI labels

UI-подписи должны строиться отдельно от technical names.

Рекомендуется:

- не использовать DB column names как текст в интерфейсе;
- держать mapping technical name → localized label;
- для таблиц и форм использовать единый glossary.

Пример:

| Technical field | UI label RU |
|---|---|
| client_id | Клиент |
| parent_unit_id | Родительское подразделение |
| org_unit_id | Подразделение |
| position_id | Должность |
| employee_code | Код сотрудника |
| is_active | Активен |
| created_at | Создано |
| updated_at | Обновлено |

Это особенно важно для экранов списков, фильтров и модальных форм.

## 11. Правила обязательности полей

Для MVP рекомендуется различать:

- **Business required** — без поля сущность бизнес-смысл теряет;
- **System required** — поле нужно системе, но пользователь может его не вводить напрямую;
- **UI required** — поле обязательно в конкретной форме;
- **Conditionally required** — поле становится обязательным только в определённом сценарии.

Пример:

- `Client.name` — business required;
- `Client.code` — system required;
- `Account.password_hash` — system required, но не UI field;
- `Account.email` — conditionally required, если email используется как login/notification channel.

## 12. Правила связности между сущностями

Минимальные связи MVP:

- Client 1 → N OrgUnit
- Client 1 → N Position
- Client 1 → N Employee
- Client 1 → N Account
- OrgUnit 1 → N child OrgUnit
- OrgUnit 1 → N Employee
- OrgUnit 1 → N Position
- Position 1 → N Employee
- Employee 1 → 0..1 Account
- Account 1 → N AccountRoleAssignment
- Role 1 → N AccountRoleAssignment
- OnboardingRun 0..N → creates Client / OrgUnit / Position / Employee / Account / Role assignments

Для словаря данных важно не просто зафиксировать саму связь, а определить, где хранится ссылка и кто является владельцем этой связи.

---

## 13. Минимальные соглашения по валидации

Рекомендуется уже на уровне словаря зафиксировать базовые validation rules:

- `code` — только допустимый набор символов, без случайной локализации;
- `name` — trimmed string, разумный max length;
- email — normalized lower-case where appropriate;
- phone — normalized format if used;
- enum fields — только значения из справочника;
- foreign keys — всегда проверяются на принадлежность тому же client scope, если включена tenant model.

---

## 14. Что особенно важно согласовать заранее

До старта полной реализации нужно принять несколько решений, иначе словарь начнёт расползаться:

1. один ли стандарт API naming — snake_case или camelCase;
2. где именно живут локализованные подписи полей;
3. нужны ли `name_ru` / `name_en` для сущностей MVP;
4. используется ли soft-delete;
5. есть ли глобальные справочники ролей и должностей, или всё tenant-local;
6. нужна ли нормализованная модель шагов onboarding run;
7. какие enum фиксируются кодами уже сейчас.

Без этих решений backend и frontend быстро начнут расходиться в деталях.

## 16. Связь словаря с другими документами

Этот документ напрямую связан со следующими артефактами:

- **ERD / data model** — определяет структуру сущностей;
- **Backend Delivery Plan** — определяет очередность реализации сущностей и сервисов;
- **Frontend Screen Map** — определяет, какие поля реально выходят на экран;
- **OpenAPI Baseline v1** — определяет контракт DTO;
- **Onboarding master scenario** — определяет, какие сущности и поля нужны мастеру запуска.

То есть Data Dictionary должен стать центральным терминологическим слоем между архитектурой и реализацией.

---

## 17. Что не должно происходить

Data Dictionary не должен превращаться:

- в случайный список колонок без бизнес-смысла;
- в копию ERD без правил использования;
- в frontend label sheet без связи с БД;
- в документ, где для одного и того же поля в разных местах используются разные названия.

Он должен быть именно каноническим справочником данных системы.

---

## 18. Acceptance criteria

Документ можно считать достаточным для MVP, если:

- перечислены все ключевые сущности MVP;
- по каждой сущности зафиксирован минимальный field set;
- определены canonical names по слоям;
- зафиксированы naming conventions;
- отделены system fields, business fields и UI fields;
- определены базовые enums и reference patterns;
- есть понятная связка с ERD, API и frontend screen model.

## 19. Практический вывод

После фиксации MVP Data Dictionary v1 следующим наиболее логичным шагом становится один из двух документов:

### Вариант A — «OpenAPI Resource Contracts v1»

Если следующий приоритет — быстро перейти к backend/frontend реализации. Тогда из словаря данных сразу выводятся:

- request/response DTO;
- list/detail/create/update contracts;
- reference payloads;
- filter/query conventions.

### Вариант B — «RBAC + Permission Matrix v1»

Если следующий приоритет — заранее стабилизировать права доступа по экранам, ресурсам и действиям.

Практически чаще всего следующий лучший шаг после Data Dictionary — именно **OpenAPI Resource Contracts v1**, потому что он превращает словарь данных в прямой контракт разработки.
