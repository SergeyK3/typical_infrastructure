# Документ №8. Frontend Delivery Plan (MVP)

## 1. Назначение документа

Frontend Delivery Plan фиксирует практический план поставки пользовательского интерфейса MVP-платформы для one-click onboarding юридических лиц, оргструктуры и назначений ролей.

Его задача — перевести архитектурную и API-проработку в управляемую последовательность frontend-реализации.

Документ задаёт:

- целевую структуру frontend-слоёв;
- набор экранов и UI-модулей;
- порядок поставки по delivery waves;
- требования к контрактам между frontend и backend;
- состав DTO/view-model на стороне UI;
- критерии готовности по каждой волне;
- минимальный набор frontend-тестов;
- инженерные решения, которые лучше зафиксировать заранее.

Этот документ должен быть симметричен Backend Delivery Plan и использоваться как рабочий delivery-ориентир для реализации интерфейса MVP.

---

## 2. Роль Frontend Delivery Plan в общем пакете

Frontend Delivery Plan связывает между собой:

- бизнес-сценарии продукта;
- мастер-сценарий создания предприятия;
- OpenAPI Baseline v1;
- backend delivery waves;
- MVP backlog by phases.

Если Backend Delivery Plan отвечает на вопрос **что и в какой последовательности реализуется на стороне сервера**, то Frontend Delivery Plan отвечает на вопрос **в каком порядке пользователь сможет реально видеть, вводить, редактировать и запускать эти процессы в интерфейсе**.

Иными словами:

- backend поставляет capabilities;
- frontend поставляет управляемый пользовательский контур работы с этими capabilities.

---

## 3. Базовые принципы frontend-реализации

### 3.1. Frontend должен идти волнами, а не экранами в хаотичном порядке

Нельзя параллельно делать все страницы сразу. Сначала должен появиться каркас приложения и сквозные UI-механизмы, затем справочники и простые CRUD-контуры, затем более сложные сущности, затем мастер-оркестрация.

### 3.2. UI должен строиться вокруг сценариев, а не вокруг таблиц базы данных

Даже если backend и БД организованы по сущностям, пользователь мыслит не таблицами, а действиями:

- создать заказчика;
- задать подразделения;
- задать должности;
- назначить сотрудников;
- выдать роли;
- запустить onboarding.

Поэтому frontend должен сначала давать человеку завершать сценарий, а не просто редактировать отдельные записи.

### 3.3. UI-контракты должны быть стабильны по DTO

Frontend не должен зависеть от внутренней формы ORM-моделей. Он должен получать стабильные API DTO и строить на них свои view-model.

### 3.4. Общие UI-паттерны должны быть унифицированы заранее

Нужно заранее выбрать и зафиксировать единый подход к:

- layout;
- navigation;
- table/list patterns;
- form patterns;
- modal/drawer patterns;
- notifications;
- optimistic / pessimistic save strategy;
- loading / empty / error states.

### 3.5. Один сложный мастер лучше, чем несколько несвязанных экранов

Для сценария создания предприятия предпочтительнее управляемый мастер или wizard, чем набор разрозненных форм без orchestration.

### 3.6. MVP должен иметь минимально достаточный admin UI, а не идеальный UI

На уровне MVP интерфейс должен быть функциональным, предсказуемым и расширяемым. Избыточная декоративность на этом этапе не нужна.

## 4. Предполагаемая frontend-архитектура

Ниже приведён рекомендуемый уровень модульной декомпозиции. Названия могут быть адаптированы под конкретный стек, но смысл разделения желательно сохранить.

### 4.1. App Shell

Отвечает за общий каркас приложения:

- root layout;
- top navigation / side navigation;
- auth-aware routing;
- breadcrumb zone;
- page title zone;
- notifications/toasts;
- modal host;
- error boundary;
- loading shell.

### 4.2. Route Modules / Pages

Отвечают за страницы и сценарные экраны:

- dashboard;
- clients;
- org units;
- positions;
- employees;
- accounts;
- onboarding runs;
- onboarding wizard;
- admin / system pages.

### 4.3. Feature Modules

Функциональные UI-модули, сгруппированные по предметной области:

- clients feature;
- org units feature;
- positions feature;
- employees feature;
- accounts feature;
- onboarding feature;
- common reference feature.

### 4.4. API Client Layer

Отвечает за работу с backend API:

- typed API client;
- request builders;
- auth header injection;
- error mapping;
- pagination helpers;
- retry policy where applicable.

### 4.5. State / Query Layer

Отвечает за получение, кэширование и инвалидацию данных:

- query hooks;
- mutation hooks;
- cache invalidation strategy;
- list/detail refresh policy;
- wizard draft state.

### 4.6. Shared UI Components

Переиспользуемые элементы:

- data table;
- search/filter bar;
- page header;
- empty state;
- inline status badge;
- confirmation dialog;
- form section;
- stepper;
- entity picker;
- assignment matrix block.

### 4.7. Form Layer

Отвечает за формы, валидацию и маппинг данных:

- form schemas;
- default values;
- client-side validation;
- backend validation error rendering;
- data normalization before submit.

### 4.8. UI Domain View-Models

Необязательный, но полезный слой для сложных экранов. Он преобразует API DTO в формат, удобный для визуализации и локальной логики UI.

## 5. Рекомендуемая структура frontend-модулей

Ниже — рекомендуемая логическая структура.

```text
frontend/
  app/
    (auth)/
    dashboard/
    clients/
    org-units/
    positions/
    employees/
    accounts/
    onboarding/
    admin/
  features/
    clients/
      api/
      components/
      forms/
      hooks/
      mappers/
      types/
    org-units/
      api/
      components/
      forms/
      hooks/
      mappers/
      types/
    positions/
    employees/
    accounts/
    onboarding/
  shared/
    api/
    ui/
    forms/
    utils/
    constants/
    types/
  widgets/
    app-shell/
    page-header/
    navigation/
```

Смысл этой структуры в том, чтобы не смешивать:

- routing;
- feature-логику;
- shared UI primitives;
- API integration;
- form schemas;
- page composition.

## 6. Разделение ответственности по слоям

### 6.1. Pages / Route Handlers

Отвечают за:

- маршруты;
- композицию страницы;
- подключение feature-компонентов;
- page-level guards;
- page metadata;
- page-level layout composition.

Не должны содержать тяжёлую бизнес-логику.

### 6.2. Feature Components

Отвечают за:

- сценарную логику внутри конкретной области;
- сборку формы/таблицы/редактора;
- связывание UI-компонентов и hooks;
- обработку действий пользователя.

### 6.3. Query / Mutation Hooks

Отвечают за:

- загрузку списков и карточек;
- создание/обновление/удаление;
- кэширование;
- инвалидацию;
- стандартизированный error handling.

### 6.4. Forms

Отвечают за:

- структуру полей;
- клиентскую валидацию;
- маппинг initial values;
- submit-payload mapping.

### 6.5. API Layer

Отвечает за:

- вызовы endpoint’ов;
- сериализацию параметров;
- десериализацию ответов;
- типизацию request/response;
- обработку HTTP-level ошибок.

### 6.6. Shared UI Layer

Отвечает за:

- единые визуальные элементы;
- повторяемые визуальные паттерны;
- общую UX-консистентность.

### 6.7. Domain View-Model / Mapper Layer

Отвечает за преобразование backend DTO в формат, удобный для UI.

Например:

- объединение display name;
- flatten дерева для таблицы;
- подсчёт derived statuses;
- группировка назначений по ролям;
- сборка step summary в wizard.

## 7. Delivery Waves для frontend

Рекомендуется поставлять frontend по следующим волнам.

1. Core Foundation
2. Reference CRUD Foundation
3. Org Units UI
4. Positions UI
5. Employees UI
6. Accounts and Roles UI
7. Onboarding Runs UI
8. Bootstrap Wizard / Orchestration UI
9. Hardening and Contract Stabilization

Ниже — состав каждой волны.

---

## 8. Wave 1 — Core Foundation

### 8.1. Цель

Создать базовый каркас приложения, на котором дальше будут собираться все бизнес-экраны.

### 8.2. Что входит

- root app shell;
- base navigation;
- auth/session wiring;
- basic route guards;
- page header pattern;
- common loading / empty / error states;
- notification/toast mechanism;
- standard confirmation dialog;
- typed API client skeleton;
- query provider / cache provider;
- base theme/tokens;
- base table and form primitives.

### 8.3. Ключевые deliverables

- приложение открывается в едином shell;
- можно безопасно подключать новые разделы;
- все API-вызовы идут через единый client;
- ошибки отображаются одинаково;
- базовые таблицы и формы уже не нужно писать с нуля.

### 8.4. Acceptance criteria

- есть единый layout;
- есть единый способ показывать loader/empty/error;
- есть единый способ отправлять GET/POST/PATCH/DELETE;
- есть базовые reusable UI-компоненты;
- есть route-level защита для закрытых разделов.

---

## 9. Wave 2 — Reference CRUD Foundation

### 9.1. Цель

Сделать эталонный CRUD-контур на простых сущностях, чтобы зафиксировать базовые UI-паттерны.

### 9.2. Сущности волны

В зависимости от окончательного MVP-состава это может быть:

- clients;
- role templates;
- position templates;
- reference dictionaries, если они нужны как отдельные каталоги.

### 9.3. Что входит

- list page;
- detail / edit page or modal;
- create form;
- delete confirmation;
- pagination/search/filter baseline;
- common form validation pattern;
- refetch / invalidate pattern after mutations.

### 9.4. Зачем нужна эта волна

Она даёт эталон, по которому дальше будут реализовываться более сложные разделы. Без этой волны есть риск, что каждый следующий экран будет построен по разным правилам.

### 9.5. Acceptance criteria

- минимум один reference-раздел полностью проходит полный CRUD-цикл;
- create/edit/delete ведут себя одинаково по UX;
- ошибки backend валидации корректно отображаются в форме;
- таблица, фильтр и форма уже можно переиспользовать дальше.

---

## 10. Wave 3 — Org Units UI

### 10.1. Цель

Дать пользователю управляемый интерфейс для построения организационной структуры клиента.

### 10.2. Что входит

- список/дерево подразделений;
- создание корневого подразделения;
- создание дочернего подразделения;
- просмотр карточки org unit;
- редактирование названия, типа, родителя, порядка;
- активация / деактивация;
- отображение иерархии;
- предотвращение некорректных перемещений, если backend поддерживает такие ограничения.

### 10.3. UI-паттерны

На этой волне нужно определить, какой базовый паттерн используется:

- tree + detail pane;
- tree + modal edit;
- table with hierarchy indentation;
- hybrid mode.

### 10.4. View-model задачи

Frontend должен уметь:

- строить иерархию из API-данных;
- раскрывать и сворачивать узлы;
- показывать путь до узла;
- отображать parent-child контекст.

### 10.5. Acceptance criteria

- пользователь может создать и отредактировать структуру подразделений;
- иерархия визуально понятна;
- CRUD org units стабилен;
- есть защита от разрушительных действий без подтверждения.

---

## 11. Wave 4 — Positions UI

### 11.1. Цель

Дать интерфейс управления должностями и их привязкой к оргструктуре.

### 11.2. Что входит

- список должностей;
- фильтр по клиенту/подразделению;
- создание должности;
- редактирование атрибутов должности;
- привязка к org unit;
- активация / деактивация;
- просмотр состава назначений по должности, если это предусмотрено API.

### 11.3. Особенности

Позиции часто стоят на границе между справочником и operational entity. Поэтому уже здесь нужно продумать:

- как показывать принадлежность к org unit;
- как показывать активность;
- как показывать role template / account linkage, если это понадобится позже.

### 11.4. Acceptance criteria

- должности можно создавать и редактировать в понятном UI;
- связь с org unit явно видна;
- список должностей можно фильтровать;
- форма не допускает отправки невалидной комбинации обязательных полей.

---

## 12. Wave 5 — Employees UI

### 12.1. Цель

Дать интерфейс управления сотрудниками и их кадровыми привязками.

### 12.2. Что входит

- список сотрудников;
- поиск по ФИО / табельному признаку / внешнему идентификатору;
- карточка сотрудника;
- создание сотрудника;
- редактирование сотрудника;
- привязка к подразделению;
- привязка к должности;
- отображение активного статуса;
- базовая история назначений, если входит в MVP.

### 12.3. Сложности

На этом этапе нужно заранее определить, как UI будет различать:

- person;
- employee record;
- assignment;
- account.

Даже если backend упрощает модель, интерфейс не должен смешивать эти сущности без необходимости.

### 12.4. Acceptance criteria

- сотрудник может быть создан и отредактирован;
- связь сотрудника с подразделением и должностью понятна;
- списки и формы устойчиво работают на типовом объёме данных;
- UI не путает кадровую запись с учётной записью.

---

## 13. Wave 6 — Accounts and Roles UI

### 13.1. Цель

Дать интерфейс управления аккаунтами и назначениями ролей.

### 13.2. Что входит

- список аккаунтов;
- карточка аккаунта;
- создание аккаунта или привязка аккаунта к сотруднику;
- назначение ролей;
- отображение активных ролей;
- revoke / deactivate role assignment;
- базовый audit-friendly вид по ролям аккаунта.

### 13.3. Ключевой UX-вопрос

Нужно заранее решить, как пользователь будет мыслить этот экран:

- как экран аккаунтов;
- как экран доступов;
- как экран назначения ролей конкретному сотруднику.

Для MVP обычно лучше один главный сценарий и один вторичный, чем несколько конкурирующих UX-моделей.

### 13.4. Acceptance criteria

- аккаунт и роли можно просматривать и менять;
- роли отображаются прозрачно и однозначно;
- нельзя случайно выдать дублирующее или некорректное назначение;
- все действия по ролям подтверждаются и обрабатываются предсказуемо.

---

## 14. Wave 7 — Onboarding Runs UI

### 14.1. Цель

Дать оператору интерфейс работы с экземплярами запуска onboarding-процесса.

### 14.2. Что входит

- список onboarding runs;
- карточка run;
- статусы run;
- отображение шагов / стадий;
- отображение ошибок;
- возможность просмотра результата bootstrap;
- возможность перезапуска допустимых операций, если это поддержано backend.

### 14.3. Что особенно важно

Это уже не просто CRUD. Здесь интерфейс должен показывать процессное состояние:

- queued / running / completed / failed;
- какая стадия выполнена;
- на каком шаге ошибка;
- что уже создано;
- какие действия ещё доступны.

### 14.4. Acceptance criteria

- пользователь видит список запусков и их статусы;
- карточка run даёт понятную картину прогресса;
- ошибки и частичные результаты видны;
- оператор может отличить успешный run от частично проваленного.

---

## 15. Wave 8 — Bootstrap Wizard / Orchestration UI

### 15.1. Цель

Собрать пользовательский мастер one-click onboarding как главный сценарный интерфейс MVP.

### 15.2. Что входит

- stepper/wizard shell;
- ввод данных клиента;
- задание базовой оргструктуры;
- задание позиций/ролей по умолчанию;
- назначение сотрудников/аккаунтов, если это входит в сценарий;
- review step;
- submit orchestration command;
- success/failure summary;
- возможность безопасного повторного открытия / просмотра результата.

### 15.3. Рекомендуемая структура мастера

Примерно:

1. Client basics
2. Org structure setup
3. Positions / templates
4. Employees / accounts / role assignments
5. Review
6. Run and result

Точная структура зависит от финального orchestration contract.

### 15.4. Ключевые UX-требования

- шаги должны быть понятными и конечными;
- нельзя потерять введённые данные при переключении шагов;
- ошибки должны возвращать пользователя к конкретному проблемному шагу;
- summary должен показывать, что именно будет создано;
- мастер не должен превращаться в хаотичный набор форм.

### 15.5. Acceptance criteria

- пользователь может пройти мастер от начала до конца;
- итоговая команда orchestration уходит в backend корректно;
- результат запуска читаем в UI;
- повторный запуск не ломает пользовательское понимание происходящего.

---

## 16. Wave 9 — Hardening and Contract Stabilization

### 16.1. Цель

Стабилизировать интерфейс после прохождения основных сценариев.

### 16.2. Что входит

- polishing empty/error/loading states;
- стабильная обработка backend validation errors;
- оптимизация рефетчей и кеш-инвалидации;
- улучшение навигации между связанными сущностями;
- улучшение таблиц, фильтров, пагинации;
- устранение UI race conditions;
- accessibility baseline;
- контрактная стабилизация DTO/view-model.

### 16.3. Acceptance criteria

- UI предсказуем в пограничных состояниях;
- нет критичных UX-разрывов между разделами;
- пользователь не теряет контекст после мутаций;
- API-контракты используются стабильно и единообразно.

---

### 17.1. Общие экраны

- login / auth entry;
- dashboard / landing;
- not found / access denied / error state pages.

### 17.2. Справочные и operational разделы

- Clients List;

- Org Units Workspace;
- Positions List/Editor;
- Employees List/Editor;
- Accounts and Roles Workspace;

## 18. Состав view-model и UI DTO

Frontend желательно проектировать не только от backend DTO, но и от UI-потребностей.

### 18.1. Примеры API DTO

- ClientListItemDto;
- ClientDetailDto;
- OrgUnitTreeNodeDto;
- PositionListItemDto;
- EmployeeListItemDto;
- AccountDetailDto;
- RoleAssignmentDto;
- OnboardingRunListItemDto;
- OnboardingRunDetailDto;
- BootstrapCommandDto;
- BootstrapResultDto.

### 18.2. Примеры UI view-model

- OrgUnitTreeVm;
- PositionRowVm;
- EmployeeCardVm;
- AccountAccessVm;
- WizardStepSummaryVm;
- RunProgressVm.

### 18.3. Почему это важно

Если этого не сделать, страницы быстро начинают содержать хаотичный mapping прямо внутри JSX/компонентов, и UI становится трудно стабилизировать.

## 19. Формы и валидация

### 19.1. Что нужно унифицировать

Нужно заранее зафиксировать единый подход к:

- required/optional fields;
- client-side validation;
- backend error rendering;
- dirty state;
- confirm-on-leave policy;
- create vs edit default values;
- select/picker loading behaviour.

### 19.2. Минимальные form-артефакты

Для каждой значимой сущности нужны:

- input schema;
- initial value mapper;
- submit payload mapper;
- error mapping contract.

### 19.3. Особое требование для wizard

У мастера должен быть отдельный draft state, а не случайный набор локальных состояний по шагам.

## 20. Навигация и UX-правила

### 20.1. Навигация

Нужно зафиксировать:

- primary navigation sections;
- section landing pattern;
- detail back-navigation;
- breadcrumb policy;
- cross-links между связанными сущностями.

### 20.2. Базовые UX-правила

- каждая страница должна явно отвечать на вопрос «что здесь можно сделать»;
- destructive actions требуют подтверждения;
- после create/edit/delete пользователь не должен терять контекст;
- списки должны иметь внятные empty states;
- status должен быть виден визуально, а не только текстом в глубине карточки.

## 21. Порядок зависимости frontend от backend

Frontend не должен ждать полного backend-завершения всего проекта. Но поставка должна идти в согласованном порядке.

Рекомендуемая зависимость такая:

1. сначала согласовать OpenAPI Baseline v1;
2. затем backend отдаёт стабильный foundation для reference CRUD;
3. после этого frontend строит reusable patterns;
4. затем backend и frontend идут синхронно по сущностям;
5. wizard и orchestration UI начинаются только тогда, когда orchestration contract уже достаточно стабилен.

Это защищает проект от ситуации, когда мастер уже нарисован, а orchestration payload ещё постоянно меняется.

## 22. Минимальный пакет frontend-тестов

На MVP не нужен чрезмерный тестовый слой, но нужен базовый защитный минимум.

### 22.1. Unit / component level

- рендер базовых reusable components;
- mapping функций DTO → VM;
- form validators;
- payload mappers.

### 22.2. Feature / integration level

- успешная загрузка list page;
- create/edit/delete сценарий хотя бы для одной reference-сущности;
- org unit create/edit flow;
- role assignment flow;
- onboarding wizard happy path.

### 22.3. End-to-end smoke level

Минимум один сквозной smoke-сценарий:

- открыть приложение;
- создать клиента;
- создать оргструктуру;
- создать должность;
- создать сотрудника;
- назначить роль;
- пройти onboarding wizard;
- увидеть результат запуска.

## 25. Ключевые инженерные решения, которые нужно принять заранее

Ниже — список решений, которые лучше не откладывать.

### 25.1. Query/state library

Нужно заранее выбрать и зафиксировать подход к server-state management.

### 25.2. Form library и validation approach

Нужно заранее определить:

- чем строятся формы;
- где живут схемы;
- как маппятся backend errors.

### 25.3. Tree representation strategy

Для org units заранее нужно решить:

- backend отдаёт already-built tree или flat list;
- где строится иерархия;
- как обрабатываются reorder/move сценарии.

### 25.4. Table standard

Нужно решить, какой паттерн считается стандартным для:

- list pages;
- sorting;
- filtering;
- row actions;
- inline status display.

### 25.5. Wizard draft persistence

Нужно заранее решить, где живёт draft мастера:

- локально в памяти;
- в URL/state;
- в local storage/session storage;
- на backend как draft resource.

### 25.6. Error model contract

Нужно заранее договориться, как backend возвращает:

- validation errors;
- domain conflicts;
- orchestration errors;
- partial success responses.

Без этого frontend будет вынужден каждый экран обрабатывать по-разному.

### 25.7. Access control rendering

Если есть role-based visibility в UI, нужно заранее определить:

- кто скрывает недоступные действия;
- как UI узнаёт capability matrix;
- как показывается access denied.
