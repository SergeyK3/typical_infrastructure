# Документ №11. Iteration Plan for MVP Sprint 1–3

## 1. Назначение документа

Iteration Plan for MVP Sprint 1–3 переводит delivery board и implementation sequence в ближайший тактический план исполнения.

Если предыдущие документы фиксировали:

- архитектуру;
- целевые контракты;
- backend и frontend delivery waves;
- sequence поставки;
- work breakdown и dependency map,

то этот документ отвечает на следующий практический вопрос:

**что именно делать в первых трёх итерациях, чтобы уже через короткий цикл получить управляемый, демонстрируемый и нарастающий результат.**

Документ задаёт:

- цель каждого спринта;
- состав sprint scope;
- зависимости между спринтами;
- ожидаемые deliverables;
- sprint checkpoints;
- definition of done на уровне итерации;
- риски перегруза спринта;
- рекомендуемую логику демонстрации результата.

---

## 2. Для чего нужен именно отдельный iteration plan

Implementation Sequence задаёт правильный порядок развития системы, но он всё ещё остаётся уровнем delivery-phases и work packages.

Для реальной работы этого недостаточно.

Команде или исполнителю нужен более прикладной слой:

- что брать в ближайший sprint;
- что не брать, даже если хочется;
- какие зависимости обязательно закрыть до следующего sprint;
- какой результат должен быть виден в конце каждой итерации.

Именно это и задаёт Iteration Plan.

---

## 3. Базовый принцип планирования Sprint 1–3

Первые три спринта должны не пытаться «сделать весь MVP», а последовательно создать:

1. foundation для устойчивой разработки;
2. первый эталонный CRUD-контур;
3. рабочую организационно-штатную основу.

То есть логика первых трёх спринтов должна быть такой:

- Sprint 1 — собрать базовую платформу и правила интеграции;
- Sprint 2 — стабилизировать первый end-to-end CRUD slice;
- Sprint 3 — вывести систему на уровень рабочей организационной модели.

Это создаёт реальную основу, на которой уже можно строить access-layer, process-layer и orchestration.

---

## 4. Планируемый горизонт первых трёх спринтов

На уровне содержания спринты рекомендуется понимать так:

- **Sprint 1:** Baseline + Foundation;
- **Sprint 2:** Reference CRUD Baseline;
- **Sprint 3:** Organization Structure + старт Staffing Foundation.

Такой горизонт даёт:

- короткий путь до первого живого результата;
- раннюю стабилизацию паттернов;
- снижение риска позднего архитектурного расползания.

---

## 5. Sprint 1 — Baseline and Foundation

## 5.1. Цель спринта

Создать минимально жизнеспособный технический и организационный контур разработки, на котором можно безопасно и предсказуемо строить бизнес-функции.

Это не sprint «про красивый функционал». Это sprint, который должен убрать хаос на старте.

## 5.2. Основной результат Sprint 1

К концу Sprint 1 должны существовать:

- согласованный baseline пакета документов;
- backend foundation runtime;
- migration foundation;
- frontend shell foundation;
- frontend integration foundation;
- базовый стиль API/error contracts.

Иными словами, после Sprint 1 проект должен перейти из состояния «описан на бумаге» в состояние «имеет рабочую среду реализации».

## 5.3. Sprint 1 Scope

### 5.3.1. Governance and baseline

В scope включаются:

- фиксация терминологии и MVP-границ;
- фиксация naming conventions;
- фиксация API baseline правил;
- фиксация error model baseline;
- фиксация delivery discipline.

### 5.3.2. Backend foundation

В scope включаются:

- структура backend-пакетов и модулей;
- app bootstrap;
- config and dependency wiring;
- logging baseline;
- health endpoint;
- базовый shared error/response style.

### 5.3.3. Database foundation

В scope включаются:

- миграционный каркас;
- правила ревизий;
- dev/test initialization flow;
- воспроизводимый database bootstrap.

### 5.3.4. Frontend foundation

В scope включаются:

- app shell;
- page frame;
- navigation skeleton;
- auth-aware route handling, если это уже входит в MVP-basis;
- API client;
- query/cache foundation;
- common loading/error/empty states;
- common feedback patterns.

## 5.4. Что сознательно не входит в Sprint 1

Не должно входить:

- полноценный бизнес-CRUD по нескольким сущностям;
- оргструктура как рабочий модуль;
- должности и сотрудники;
- аккаунты и роли;
- onboarding wizard;
- process-layer логика.

Если это начнёт входить в Sprint 1, sprint почти наверняка потеряет фокус.

## 5.5. Sprint 1 Deliverables

Итоговыми deliverables должны быть:

1. baseline-ready document set;
2. runnable backend foundation;
3. working migration flow;
4. runnable frontend shell;
5. unified frontend-backend integration baseline;
6. skeleton of first integration-ready section.

## 5.6. Sprint 1 Checkpoint

Контрольный вопрос в конце спринта:

**можно ли теперь без импровизации начать строить первый CRUD slice?**

Если ответ «да», Sprint 1 успешен.

## 5.7. Sprint 1 Definition of Done

Sprint 1 считается завершённым, если:

- backend и frontend устойчиво запускаются;
- миграции воспроизводимы;
- базовые правила API и error handling согласованы;
- shell и integration primitives готовы к использованию;
- команда понимает, по какому шаблону строится следующая сущность.

## 5.8. Demo в конце Sprint 1

Демонстрация должна показать не бизнес-функцию, а устойчивый каркас:

- backend service boot;
- migration flow;
- frontend shell;
- API connectivity;
- единый стиль ошибок и состояний.

---

## 6. Sprint 2 — First Reference CRUD Slice

## 6.1. Цель спринта

Собрать первый полностью рабочий сквозной CRUD-контур на простой reference-сущности и тем самым стабилизировать шаблон реализации для следующих модулей.

## 6.2. Основной результат Sprint 2

К концу Sprint 2 должна существовать одна reference-сущность, которая проходит полный цикл:

- schema;
- migration;
- backend CRUD;
- API contract;
- frontend list/detail/create/edit/delete flow;
- acceptance pass.

То есть Sprint 2 должен дать первый **живой end-to-end slice**.

## 6.3. Sprint 2 Scope

### 6.3.1. Reference data model

В scope включаются:

- таблица и модель выбранной reference-сущности;
- миграция;
- базовые constraints.

### 6.3.2. Backend CRUD slice

В scope включаются:

- repository;
- service;
- router;
- request/response DTO;
- create/list/detail/update/delete or deactivate contract.

### 6.3.3. Frontend CRUD slice

В scope включаются:

- list page;
- create form;
- edit flow;
- delete/deactivate confirmation;
- basic search/filter, если он нужен по baseline.

### 6.3.4. Contract Freeze A

В scope включаются:

- validation error contract stabilization;
- list response pattern;
- mutation response pattern;
- reusable CRUD pattern confirmation.

## 6.4. Что сознательно не входит в Sprint 2

Не должно входить:

- сразу несколько reference-сущностей без необходимости;
- оргструктурное дерево;
- staffing-сущности;
- role assignment;
- onboarding-runs;
- wizard.

Задача Sprint 2 — не объём, а эталон.

## 6.5. Sprint 2 Deliverables

Итогом должны стать:

1. первый reference CRUD backend slice;
2. первый reference CRUD frontend slice;
3. стабилизированный CRUD template;
4. Contract Freeze A;
5. первый business-adjacent demo-ready module.

## 6.6. Sprint 2 Checkpoint

Контрольный вопрос в конце спринта:

**можно ли теперь по этому образцу относительно быстро и без смены правил реализовывать org units и другие сущности?**

Если ответ «да», Sprint 2 выполнен правильно.

## 6.7. Sprint 2 Definition of Done

Sprint 2 считается завершённым, если:

- reference-сущность проходит полный CRUD-цикл;
- frontend и backend используют единый контракт;
- ошибки отображаются предсказуемо;
- create/edit/delete поведение уже считается эталонным;
- следующий модуль можно строить через reuse этого шаблона.

## 6.8. Demo в конце Sprint 2

Демонстрация должна показать:

- создание записи;
- появление записи в списке;
- открытие и редактирование;
- удаление или деактивацию;
- обработку ошибки валидации.

---

## 7. Sprint 3 — Organization Structure and Staffing Start

## 7.1. Цель спринта

Построить рабочий контур организационной структуры и начать формировать штатную основу MVP.

Sprint 3 — это первый sprint, в котором система должна начать напоминать предметную платформу, а не только инфраструктуру и шаблоны.

## 7.2. Основной результат Sprint 3

К концу Sprint 3 должны существовать:

- рабочая модель org units;
- backend и frontend контур оргструктуры;
- принятый org structure acceptance pass;
- стартовый backend/UI slice по positions либо как минимум полностью готовая подготовка к нему.

То есть после Sprint 3 платформа уже должна уметь выражать **структуру предприятия**.

## 7.3. Sprint 3 Scope

### 7.3.1. Org units data and backend

В scope включаются:

- org units schema;
- parent-child model;
- constraints;
- list/detail/create/update services;
- hierarchy retrieval logic.

### 7.3.2. Org units frontend workspace

В scope включаются:

- hierarchy page/workspace;
- create root unit;
- create child unit;
- edit unit;
- activation/deactivation;
- hierarchy rendering.

### 7.3.3. Org structure acceptance pass

В scope включаются:

- проверка CRUD для org units;
- проверка корректности иерархии;
- проверка визуального поведения UI;
- проверка связности с клиентским контуром.

### 7.3.4. Staffing preparation or initial positions slice

В зависимости от реального темпа разработки в Sprint 3 допускается один из двух уровней:

**Вариант A — консервативный:**
- полностью завершить org structure;
- подготовить schema/API/UI design для positions.

**Вариант B — более сильный:**
- завершить org structure;
- начать initial positions slice:
  - schema;
  - migration;
  - basic backend CRUD;
  - базовый list/form UI.

Для MVP v1 более предпочтителен вариант B, если Sprint 1–2 завершены без перегруза и долгов.

## 7.4. Что сознательно не входит в Sprint 3

Не должно входить:

- полноценные сотрудники как уже зрелый модуль;
- accounts and roles;
- onboarding runs;
- wizard/orchestration;
- hardening всей системы.

## 7.5. Sprint 3 Deliverables

Минимально обязательные deliverables:

1. org units data model;
2. org units backend slice;
3. org units frontend workspace;
4. accepted organization structure module.

Желательные дополнительные deliverables:

5. initial positions slice or staffing-ready contract package.

## 7.6. Sprint 3 Checkpoint

Контрольный вопрос в конце спринта:

**можно ли теперь использовать систему для выражения структуры предприятия и опираться на эту структуру при построении staffing-layer?**

Если ответ «да», Sprint 3 выполнен правильно.

## 7.7. Sprint 3 Definition of Done

Sprint 3 считается завершённым, если:

- оргструктура управляется через UI;
- hierarchy backend стабилен;
- структура визуально понятна;
- следующий слой positions может опираться на уже устойчивую модель org units.

Если дополнительно начат positions slice — это усиливает результат, но не должно ломать завершение org structure.

## 7.8. Demo в конце Sprint 3

Демонстрация должна показать:

- создание структуры предприятия;
- добавление корневых и дочерних подразделений;
- редактирование узлов;
- понятное отображение иерархии;
- при наличии — первые шаги по должностям.

---

## 8. Зависимости между Sprint 1–3

### Sprint 1 → Sprint 2

Sprint 2 не должен стартовать в полном объёме, если Sprint 1 не дал:

- рабочий migration flow;
- стабильный backend runtime;
- stable frontend integration baseline;
- согласованный error contract.

### Sprint 2 → Sprint 3

Sprint 3 не должен идти в полноценную оргструктуру, если Sprint 2 не дал:

- эталонный CRUD pattern;
- первый принятый end-to-end slice;
- Contract Freeze A.

### Почему это важно

Именно через эту зависимость уменьшается риск, что org units и staffing начнут реализовываться на ещё плавающих UI/API правилах.

---

## 9. Что может идти параллельно внутри первых трёх спринтов

### В Sprint 1 допустим параллелизм

- backend runtime foundation;
- migration foundation;
- frontend shell;
- frontend integration primitives.

Но governance baseline желательно закрыть в начале, а не в конце.

### В Sprint 2 допустим параллелизм

- backend CRUD slice;
- frontend reusable CRUD components;
- форма и list page.

Но contract stabilization не должно откладываться на потом.

### В Sprint 3 допустим параллелизм

- org units backend;
- проектирование hierarchy UI;
- базовая positions preparation.

Но полноценный positions module не должен съесть весь sprint, если из-за этого org structure останется недоделанным.

---

## 10. Основные риски Sprint 1–3

## 10.1. Риск Sprint 1 — перегруз foundation-спринта бизнес-логикой

Симптом:

- sprint превращается в хаотичную смесь foundation и случайных бизнес-сущностей.

Последствие:

- foundation остаётся недостроенным, а бизнес-модули строятся на слабой базе.

## 10.2. Риск Sprint 2 — попытка взять слишком много сущностей

Симптом:

- вместо эталона команда делает два-три неполных CRUD-контурa.

Последствие:

- шаблон так и не стабилизируется.

## 10.3. Риск Sprint 3 — преждевременный заход в staffing и access-layer

Симптом:

- positions, employees и roles начинают развиваться раньше, чем принята org structure.

Последствие:

- ссылки и контракты начинают плавать.

## 10.4. Общий риск — отсутствие sprint exit discipline

Симптом:

- sprint закрывается по ощущению, а не по deliverables и definition of done.

Последствие:

- проект формально движется, но фактическая готовность не нарастает.

---

## 11. Рекомендуемый формат результатов по спринтам

Чтобы iteration plan был реально исполнимым, по каждому sprint полезно фиксировать итоги в одном формате:

- Sprint Goal;
- In-Scope;
- Out-of-Scope;
- Deliverables;
- Checkpoint;
- Demo Story;
- Definition of Done;
- Risks / Carry-over items.

Именно такой формат рекомендуется использовать в дальнейшем для Sprint 4+.

## 12. Сводная таблица Sprint 1–3

| Sprint | Основная цель | Основной результат | Что обязательно должно быть готово |
|---|---|---|---|
| Sprint 1 | Baseline + Foundation | Рабочая среда реализации | Backend foundation, migrations, frontend shell, integration baseline |
| Sprint 2 | First Reference CRUD Slice | Первый end-to-end CRUD | Reference schema/API/UI, CRUD template, Contract Freeze A |
| Sprint 3 | Organization Structure + Staffing Start | Рабочая оргструктура | Org units model/API/UI, hierarchy acceptance, старт positions или staffing prep |

## 13. Как понять, что Sprint 1–3 прошли правильно

Первые три спринта считаются пройденными правильно, если к их концу проект находится в такой точке:

- система имеет устойчивый foundation;
- есть минимум один эталонный CRUD-модуль;
- оргструктура уже управляется через UI;
- подготовлена прочная основа для positions/employees;
- команда не вынуждена менять базовые правила на каждом следующем модуле.

Если этого нет, значит один из первых трёх спринтов был перегружен, недозакрыт или нарушил sequencing discipline.

---

## 14. Что логично планировать после Sprint 3

После Sprint 3 следующий тактический горизонт будет выглядеть так:

- Sprint 4 — Positions and Employees;
- Sprint 5 — Accounts and Role Assignment;
- Sprint 6 — Onboarding Runs and Process Visibility;
- Sprint 7 — Bootstrap Orchestration and Wizard;
- Sprint 8 — Hardening and Pilot Readiness.

То есть именно Sprint 1–3 создают основу для оставшегося пути к MVP.

---

## 15. Acceptance criteria для документа

Iteration Plan for MVP Sprint 1–3 считается достаточным, если:

- у каждого из первых трёх спринтов есть чёткая цель;
- определены in-scope и out-of-scope границы;
- зафиксированы deliverables и checkpoints;
- понятны зависимости между спринтами;
- зафиксированы основные риски перегруза;
- план можно использовать как реальный тактический ориентир исполнения.

---

## 16. Практический вывод

После фиксации этого документа проект уже имеет почти полный pre-execution пакет:

- архитектурную рамку;
- delivery plans;
- implementation sequence;
- work breakdown;
- iteration plan первых спринтов.

Следующий практичный шаг зависит от режима работы:

1. если нужен управленческий запуск исполнения — логично сделать **Sprint Board Template / Work Package Card Template**;
2. если нужен более сильный пользовательский слой — логично сделать **Frontend Screen Map + Navigation Model**;
3. если нужен уже почти прямой переход к разработке — логично сделать **OpenAPI Baseline v1 — expanded endpoint contracts** или **MVP Data Dictionary v1**.

Для комплекта pre-implementation kit особенно сильным следующим шагом будет **Frontend Screen Map + Navigation Model**, потому что он замкнёт delivery-пакет со стороны реального пользовательского интерфейса.
