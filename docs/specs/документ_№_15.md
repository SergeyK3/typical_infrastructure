# Документ №15. RBAC + Permission Matrix v1

## 1. Назначение документа

Этот документ фиксирует базовую модель разграничения доступа для MVP-платформы на уровне:

- ролей;
- областей действия ролей;
- ресурсов;
- действий;
- экранов;
- API endpoint’ов;
- административных исключений.

Его задача — устранить двусмысленность в вопросах:

- кто что видит;
- кто что может создавать, редактировать, запускать и подтверждать;
- какие действия ограничены scope’ом клиента или подразделения;
- какие действия доступны только системным администраторам;
- как права доступа соотносятся с backend API и frontend navigation.

---

## 2. Что должен зафиксировать документ

RBAC + Permission Matrix v1 должен определить:

1. набор ролей MVP;
2. типы ролей;
3. scope model ролей;
4. перечень защищаемых ресурсов;
5. перечень допустимых действий по ресурсам;
6. mapping role → permissions;
7. правила visibility и actionability;
8. правила для admin-only действий;
9. правила для onboarding и orchestration actions;
10. связь прав с экранной моделью и API contracts.

---

## 3. Базовые принципы RBAC для MVP

Для MVP рекомендуется использовать не чрезмерно гибкую, а устойчивую и объяснимую модель:

- **role-based access first**;
- scope-aware permissions;
- deny by default;
- explicit elevated permissions;
- минимальное число специальных исключений;
- separation between visibility and mutability.

### Core principle

Пользователь может:

1. **видеть** ресурс;
2. **открывать детали** ресурса;
3. **создавать** сущности;
4. **редактировать** сущности;
5. **запускать orchestration actions**;
6. **выполнять admin-only actions**

только если это явно разрешено его ролью и областью действия.

---

## 4. RBAC model layers

В MVP права следует рассматривать на трёх слоях:

### 4.1. Role layer
Кто пользователь по своей функции в системе.

### 4.2. Scope layer
На какой участок данных распространяется его роль:

- global
- client
- org_unit

### 4.3. Permission layer
Какие действия разрешены над каким ресурсом.

Итоговое право = **role + scope + action + resource**.

---

## 5. Role taxonomy for MVP

Рекомендуемый минимальный набор ролей MVP:

1. `super_admin`
2. `platform_admin`
3. `client_admin`
4. `org_admin`
5. `hr_manager`
6. `manager`
7. `viewer`
8. `onboarding_operator`

При необходимости часть ролей может быть объединена на первом этапе, но логически они должны быть различимы.

## 6. Canonical role definitions

## 6.1. super_admin

### Назначение
Полный системный контроль над всей платформой, всеми клиентами, системными ролями и административными действиями.

### Scope
- global

### Typical usage
- root administration
- diagnostics
- contract stabilization
- support of exceptional cases

---

## 6.2. platform_admin

### Назначение
Операционный системный администратор платформы, управляющий tenant-level конфигурацией и системными справочниками в допустимых пределах.

### Scope
- global

### Typical usage
- создание/поддержка клиентов
- контроль onboarding
- управление справочниками платформенного уровня
- поддержка аккаунтов и ролей

---

## 6.3. client_admin

### Назначение
Администратор конкретного клиента / компании.

### Scope
- client

### Typical usage
- ведение оргструктуры клиента
- управление должностями, сотрудниками, учётками клиента
- назначение ролей внутри клиента
- запуск onboarding для своего клиента

---

## 6.4. org_admin

### Назначение
Администратор подразделения или сегмента структуры внутри клиента.

### Scope
- org_unit

### Typical usage
- ведение части оргструктуры;
- просмотр и редактирование сущностей в рамках допустимого подразделения и его дочернего дерева, если это разрешено.

---

## 6.5. hr_manager

### Назначение
Функциональная роль для работы с сотрудниками, позициями, частью account flows и кадровыми сценариями.

### Scope
- client or org_unit

### Typical usage
- создание сотрудников;
- привязка сотрудников к должностям;
- частичная работа с аккаунтами.

---

## 6.6. manager

### Назначение
Руководитель, который в MVP в основном просматривает данные и, возможно, подтверждает ограниченные управленческие действия в будущем.

### Scope
- org_unit or client

### Typical usage
- просмотр структуры и состава;
- ограниченный доступ к людям и подразделениям своего контура.

---

## 6.7. viewer

### Назначение
Роль только на просмотр.

### Scope
- client or org_unit

### Typical usage
- readonly access;
- проверка структуры;
- аудит / ознакомление.

---

## 6.8. onboarding_operator

### Назначение
Оператор запуска мастера развертывания и контроля onboarding run.

### Scope
- global or client

### Typical usage
- проверка payload;
- preview;
- execute onboarding run;
- мониторинг результата.

---

## 7. Scope model

Для MVP желательно зафиксировать три типа области действия:

### 7.1. Global scope
Роль действует на всю платформу.

Примеры:
- `super_admin`
- `platform_admin`

### 7.2. Client scope
Роль действует только в рамках одного клиента.

Примеры:
- `client_admin`
- `hr_manager`
- `viewer`

### 7.3. Org unit scope
Роль действует только в рамках подразделения и, если разрешено, его дочернего дерева.

Примеры:
- `org_admin`
- `manager`
- `viewer`

---

## 8. Scope inheritance policy

Это критически важный слой.

Для MVP рекомендуется принять следующие правила:

### Global scope
Видит и действует везде.

### Client scope
Видит и редактирует только сущности данного клиента.

### Org unit scope
По умолчанию действует на:

- сам org unit;
- дочерние org units — **только если явно включено** policy-правилом.

### Recommended MVP policy

Для простоты первой версии:

- `org_unit` scope **может видеть своё поддерево**;
- редактирование поддерева допускается только для ролей, где это явно разрешено.

## 10. Permission action vocabulary

Для согласованности матрицы рекомендуется фиксировать единый словарь действий:

- `list`
- `view`
- `create`
- `update`
- `deactivate`
- `delete`
- `assign`
- `unassign`
- `validate`
- `preview`
- `execute`
- `activate`
- `block`
- `reset_password`
- `view_all_scopes`

### Notes

- `list` и `view` не одно и то же;
- `create` и `assign` не одно и то же;
- `deactivate` и `delete` нужно различать;
- orchestration actions (`validate`, `preview`, `execute`) должны жить отдельно от CRUD.

---

## 11. Visibility vs mutability

Это нужно зафиксировать отдельно.

Пользователь может иметь право:

- видеть список сущностей;
- открывать карточку;
- не иметь права редактировать.

Пример:

`manager` может:
- видеть сотрудников своего блока;
- открывать карточки;
- не создавать и не редактировать их.

Это значит, что в матрице нужно различать:

- visibility permissions;
- action permissions.

## 14. Navigation visibility policy

Frontend navigation не должна показывать разделы, куда роль заведомо не имеет доступа.

### Recommended rule

Навигация строится по двум критериям:

1. есть ли доступ к экрану;
2. есть ли хотя бы `list` permission по ключевому ресурсу экрана.

### Example

Если у `viewer` нет доступа к Accounts & Roles, раздел не должен отображаться в primary navigation.

---

## 15. Button/action visibility policy

Даже внутри доступного экрана элементы действий должны скрываться или блокироваться по permission matrix.

### Examples

- кнопка **Create Employee** видна только ролям с `employee.create`;
- кнопка **Edit Org Unit** видна только ролям с `org_unit.update`;
- кнопка **Execute Onboarding** видна только ролям с `onboarding_run.execute`;
- кнопка **Reset Password** — только admin class.

### Recommended UX rule

- если действие принципиально недоступно — не показывать кнопку;
- если действие контекстно недоступно из-за состояния объекта — показывать disabled + reason, если это улучшает UX.

---

## 16. API authorization policy

Каждый endpoint должен проверяться минимум по двум осям:

1. **resource permission**
2. **scope ownership**

### Example

Чтобы выполнить:

`PATCH /employees/{id}`

нужно:

- иметь `employee.update`;
- иметь доступ к клиенту/подразделению данного сотрудника.

Простого наличия роли недостаточно без проверки scope.

---

## 17. Scope resolution rules

Для backend нужно заранее определить, как вычисляется effective scope.

### Recommended approach

- global roles bypass tenant filters;
- client-scoped roles получают `client_id` assignment;
- org-unit-scoped roles получают `org_unit_id` assignment;
- для org-unit scope backend должен уметь получить разрешённый subtree.

### Important

Нельзя проверять только роль без её assignment context.

---

## 18. Conflict between multiple roles

В MVP возможны пользователи с несколькими ролями.

### Recommended resolution rule

Используется **permission union**, но scope применяется только в рамках соответствующих assignment’ов.

То есть:

- если у пользователя есть `viewer` в одном org unit;
- и `hr_manager` в другом client scope;

его effective rights складываются, но не становятся глобальными.

---

## 19. Special admin-only actions

Нужно отдельно зафиксировать набор чувствительных действий.

### Admin-only actions for MVP

- client create/update/deactivate;
- role catalog create/update;
- password reset;
- account block/activate;
- cross-client role assignment;
- global onboarding execution;
- access to all scopes without filter.

### Minimal allowed roles

- `super_admin`
- `platform_admin`
- часть действий — `client_admin` в пределах своего клиента

---

## 20. Default deny policy

Если permission явно не выдано, оно считается запрещённым.

Это должно действовать для:

- экранов;
- API methods;
- скрытых admin actions;
- reference endpoints;
- wizard execution.

---

## 21. Read vs edit scope mismatch prevention

Нужно специально предотвратить ситуацию:

- сущность видна в списке;
- но detail/action неожиданно недоступны без понятной причины.

### Recommended rule

Если роль имеет `list` и `view` в пределах scope, detail endpoint должен быть консистентен с list visibility.

Если `update` запрещён, карточка всё равно должна открываться в readonly-режиме, а не ломаться на 403 без ясной причины.

Это особенно важно для frontend UX.

---

## 22. Suggested MVP role bundle simplification

Чтобы не перегрузить первую версию, можно зафиксировать рабочую схему из четырёх фактически используемых классов доступа:

1. **Global Admin**
   - `super_admin`
   - `platform_admin`

2. **Client Admin**
   - `client_admin`

3. **Operational HR / Structure Editor**
   - `hr_manager`
   - `org_admin`

4. **Read Only**
   - `manager`
   - `viewer`

5. **Onboarding Specialist**
   - `onboarding_operator`

Это упростит первую реализацию guards и навигации.

## 23. Recommended enforcement layers

RBAC должен применяться на нескольких уровнях:

### Backend
- endpoint guards;
- service-level scope checks;
- repository/query filtering by effective scope.

### Frontend
- navigation filtering;
- screen mode switching;
- button visibility;
- readonly forms.

### API contract
- документированные forbidden/conflict scenarios.

## 24. Mapping to OpenAPI contracts

RBAC-документ должен быть совместим с OpenAPI Resource Contracts v1.

Пример связки:

- `GET /employees` → требует `employee.list`
- `GET /employees/{id}` → требует `employee.view`
- `POST /employees` → требует `employee.create`
- `PATCH /employees/{id}` → требует `employee.update`
- `POST /onboarding-runs/{id}/execute` → требует `onboarding_run.execute`

То есть permission vocabulary должен прямо ложиться на endpoint groups.

## 26. Audit and traceability notes

Для чувствительных действий желательно фиксировать audit trail.

Особенно для:

- role assignments;
- password resets;
- account blocks;
- onboarding execution;
- client updates;
- structural changes in org units.

Даже если полноценный audit subsystem ещё не реализован, модель прав должна это предусматривать.

## 27. What should not happen

RBAC-модель не должна допускать:

- скрытой эскалации прав через ref endpoints;
- доступа к данным другого клиента через foreign key подстановки;
- ситуации, когда frontend скрывает кнопку, но backend не проверяет право;
- ситуации, когда backend проверяет только роль, но не scope;
- неявных исключений без явной фиксации в policy.

---

## 28. Acceptance criteria

Документ можно считать достаточным для MVP, если:

- определён минимальный набор ролей;
- зафиксированы scope types;
- перечислены защищаемые ресурсы;
- определён словарь действий;
- составлена role/resource/action matrix;
- описаны screen access rules;
- описаны navigation/button visibility rules;
- описаны scope resolution rules;
- зафиксированы admin-only actions;
- зафиксирован default deny policy;
- матрица совместима с OpenAPI contracts.

## 29. Практический вывод

После фиксации RBAC + Permission Matrix v1 базовый архитектурный пакет MVP становится почти замкнутым:

- есть концепция;
- есть ERD;
- есть delivery plan;
- есть screen map;
- есть data dictionary;
- есть API resource contracts;
- есть permission model.

Следующий наиболее сильный шаг — уже не общий архитектурный, а более прикладной.

Наиболее логичные варианты:

### Вариант A — «Документ №16. Frontend View Models + UI State Contracts»

Если следующим приоритетом является ускорение frontend-реализации:

- table schemas;
- form models;
- modal contracts;
- loading/empty/error states;
- editable vs readonly screen modes.

### Вариант B — «Документ №16. Backend Application Services Map»

Если следующим приоритетом является ускорение backend-реализации:

- services;
- use cases;
- orchestration boundaries;
- transaction boundaries;
- repositories.

### Вариант C — «Документ №16. MVP Implementation Backlog (Epics → Features → Tasks)»

Если следующим приоритетом является переход от архитектуры к реальному execution plan.

На практике самый сильный следующий шаг сейчас — **MVP Implementation Backlog (Epics → Features → Tasks)**, потому что он переведёт весь уже собранный пакет из уровня архитектуры в уровень конкретного плана работ.
