# Документ №9. Implementation Sequence v1

## 1. Назначение документа

Implementation Sequence v1 фиксирует единую практическую последовательность реализации MVP-системы.

Его задача — свести в один исполнимый маршрут:

- архитектурную концепцию;
- OpenAPI Baseline v1;
- Backend Delivery Plan;
- Frontend Delivery Plan;
- мастер-сценарий one-click onboarding;
- MVP Backlog by Phases.

Если предыдущие документы описывали систему по слоям и по направлениям работ, то этот документ отвечает на главный практический вопрос:

**в каком порядке реально строить систему, чтобы разработка шла управляемо, без лишних возвратов и без преждевременной сборки нестабильных частей.**

Именно этот документ переводит пакет из стадии архитектурного проектирования в стадию координируемой implementation-поставки.

---

## 2. Что именно должен решить этот документ

Implementation Sequence должен зафиксировать:

- порядок delivery increments;
- зависимости между backend, frontend и API;
- момент, когда можно начинать каждую следующую волну;
- точки стабилизации контрактов;
- порядок миграций данных и схемы;
- момент появления демонстрируемых результатов;
- минимальные критерии готовности по этапам;
- рекомендуемую дисциплину коммитов и интеграций.

Этот документ нужен, чтобы избежать типовых ошибок ранней реализации:

- frontend начинает строить wizard до стабилизации orchestration contract;
- backend параллельно меняет DTO на нескольких сущностях;
- миграции идут в конфликтном порядке;
- сложные сценарии собираются раньше, чем стабилизированы базовые CRUD-контуры;
- проект выглядит активным, но не даёт ни одного устойчивого demo-сценария.

---

## 3. Основной sequencing principle

Ключевой принцип реализации:

**сначала foundation, затем стабильные CRUD-контуры, затем связанная кадрово-организационная модель, затем process-layer, затем orchestration, затем hardening.**

Это означает, что проект не должен начинаться с самого эффектного сценария. Он должен начинаться с тех слоёв, без которых этот сценарий будет хрупким.

Практически это даёт такой порядок:

1. foundation platform;
2. API baseline stabilization;
3. simple reference CRUD;
4. organizational structure;
5. positions and staffing basis;
6. employees and account-role layer;
7. onboarding runs and process visibility;
8. bootstrap orchestration and wizard;
9. hardening and pilot readiness.

---

## 4. Логика зависимости между слоями

Ниже приведена базовая логика зависимости.

### 4.1. Architecture → API

Сначала должна быть зафиксирована минимальная модель системы и набор MVP-endpoint’ов.

Без этого невозможно:

- устойчиво писать backend routers/schemas;
- проектировать frontend forms/list pages;
- тестировать orchestration contract.

### 4.2. API → Backend Foundation

После фиксации baseline API backend реализует foundation: общие подходы, каркас слоёв, базовые сущности, миграционный контур.

### 4.3. Backend Foundation → Frontend Foundation

Frontend может начинать свой foundation почти параллельно, но он не должен опережать backend по нестабильным domain-контрактам. Он может строить:

- shell;
- общие компоненты;
- query/form infrastructure;
- table/list/form patterns.

### 4.4. Stable CRUD → Scenario UI

Только после того как базовые CRUD-сущности устойчивы, имеет смысл собирать сценарные экраны и wizard.

### 4.5. Process Layer → Wizard

Экран orchestration и one-click onboarding должен стартовать только тогда, когда backend уже умеет:

- принимать orchestration command;
- создавать onboarding run;
- возвращать статус run;
- давать диагностируемый результат выполнения.

## 6. Phase 0 — Baseline Alignment

### 6.1. Цель

Свести все исходные архитектурные решения в минимально непротиворечивую baseline-конфигурацию перед началом активной реализации.

### 6.2. Что должно быть зафиксировано

- концептуальная модель данных;
- OpenAPI Baseline v1;
- мастер-сценарий one-click onboarding;
- Backend Delivery Plan;
- Frontend Delivery Plan;
- MVP backlog by phases;
- ключевые naming conventions;
- политика идентификаторов;
- минимальная error model policy.

### 6.3. Что должно стать выходом фазы

- единый baseline-пакет документов;
- список сущностей первой волны;
- список endpoint’ов первой волны;
- согласованный терминологический словарь;
- стартовая последовательность коммитов и миграций.

### 6.4. Gate to next phase

Переход дальше возможен, если:

- нет открытого противоречия между ERD, API baseline и onboarding scenario;
- понятно, какие сущности входят в MVP;
- зафиксировано, что wizard не стартует раньше process-layer.

---

## 7. Phase 1 — Core Foundation

### 7.1. Цель

Подготовить базовый runtime-каркас backend и frontend, на котором потом будут безопасно наращиваться бизнес-функции.

### 7.2. Backend scope

- структура модулей backend;
- app bootstrap;
- dependency wiring;
- базовые настройки конфигурации;
- health endpoints / service bootstrapping;
- базовый migration flow;
- базовые shared DTO/error envelope conventions;
- logging baseline;
- стандарт ответа на ошибки и validation failures.

### 7.3. Frontend scope

- app shell;
- navigation shell;
- auth/session integration;
- API client foundation;
- query/cache foundation;
- базовые form/table primitives;
- common loading/error/empty states;
- confirmation dialog / toast policy.

### 7.4. Deliverables фазы

- backend запускается с чистым foundation;
- frontend открывается в едином shell;
- есть единый API client и единый подход к ошибкам;
- есть минимальный жизнеспособный dev-runtime.

### 7.5. Gate to next phase

Переход дальше возможен, если:

- миграции применяются предсказуемо;
- backend и frontend foundation не содержат архитектурных конфликтов;
- есть единый стиль DTO и error handling.

---

## 8. Phase 2 — Reference CRUD Baseline

### 8.1. Цель

Построить эталонный сквозной CRUD-контур на простых сущностях, чтобы отладить стиль поставки и стабилизировать стандартный API/UI-паттерн.

### 8.2. Backend scope

- таблицы и модели reference-сущностей;
- repositories/services/routers для этих сущностей;
- create/list/get/update/deactivate/delete baseline;
- DTO request/response первой волны;
- pagination/search/filter baseline.

### 8.3. Frontend scope

- первый list screen;
- create/edit form;
- delete confirmation;
- empty/error handling;
- стандартный mutation-refresh flow.

### 8.4. Зачем эта фаза критична

Она формирует эталон реализации, на который будут опираться все последующие разделы. Если этот паттерн не стабилизирован, дальше проект начнёт расползаться по стилям реализации.

### 8.5. Demo milestone

Первая демонстрация должна показать:

- сущность можно создать;
- она появляется в списке;
- её можно открыть и отредактировать;
- ошибки валидируются предсказуемо.

### 8.6. Gate to next phase

Переход дальше возможен, если:

- хотя бы один reference-раздел проходит полный CRUD-цикл;
- backend DTO и frontend forms уже можно копировать как шаблон;
- подтвержден единый контракт validation errors.

---

## 9. Phase 3 — Org Structure Foundation

### 9.1. Цель

Построить устойчивый контур организационной структуры клиента.

### 9.2. Backend scope

- org units model;
- parent-child relationship;
- create/update/list/detail operations;
- базовая иерархическая валидация;
- constraints на некорректные связи;
- DTO для flat/tree retrieval, в зависимости от выбранного подхода.

### 9.3. Frontend scope

- org units workspace;
- tree or hierarchy list;
- create root and child units;
- edit unit form;
- activation/deactivation;
- hierarchy display behaviour.

### 9.4. Почему это должно идти раньше staffing

Потому что должности и сотрудники почти всегда привязываются к оргструктуре. Если слой org units не стабилен, всё остальное будет опираться на меняющуюся основу.

### 9.5. Demo milestone

- можно создать предприятие с базовым набором подразделений;
- дерево читается визуально;
- редактирование структуры не ломает контур данных.

### 9.6. Gate to next phase

Переход дальше возможен, если:

- org structure управляется через UI;
- backend гарантирует базовую целостность parent-child модели;
- понятно, как positions будут ссылаться на org units.

---

## 10. Phase 4 — Staffing Foundation

### 10.1. Цель

Построить кадрово-штатную основу: должности и сотрудники как рабочие сущности системы.

### 10.2. Backend scope

- positions model;
- employees model;
- привязка positions к org units;
- привязка employees к positions/org units в согласованной форме;
- DTO list/detail/create/update для positions и employees;
- базовые ограничения на целостность кадровых связей.

### 10.3. Frontend scope

- positions screens;
- employees screens;
- формы назначения подразделения и должности;
- search/filter;
- понятная визуализация связей between employee / position / org unit.

### 10.4. Что нельзя делать в этой фазе

Не нужно преждевременно смешивать кадровую модель с аккаунтами, доступами и process-layer логикой. Сначала должна стабилизироваться штатная основа.

### 10.5. Demo milestone

- есть оргструктура;
- к подразделениям добавлены должности;
- к должностям/подразделениям добавлены сотрудники;
- списки и карточки отображают это предсказуемо.

### 10.6. Gate to next phase

Переход дальше возможен, если:

- org unit, position, employee образуют понятную рабочую модель;
- frontend не путает кадровую запись с аккаунтом;
- ограничения данных уже не вызывают хаотичных правок схемы.

---

## 11. Phase 5 — Access and Role Assignment Layer

### 11.1. Цель

Добавить системный слой аккаунтов и ролей поверх уже стабилизированной кадровой модели.

### 11.2. Backend scope

- accounts model;
- account-role assignments;
- возможно, account-employee link;
- role templates / role dictionaries, если они входят в MVP;
- services для назначения и отзыва ролей;
- guard/capability baseline, если это уже нужно для UI.

### 11.3. Frontend scope

- accounts list/detail;
- role assignment workspace;
- назначение ролей сотруднику/аккаунту;
- отображение набора ролей;
- revoke/deactivate actions.

### 11.4. Почему эта фаза не должна идти раньше

Если начать назначать роли до стабилизации сотрудников и должностей, то access-layer будет опираться на нестабильные ссылки и начнёт требовать преждевременных переделок.

### 11.5. Demo milestone

- сотрудник связывается с аккаунтом;
- аккаунту назначаются роли;
- UI показывает роли прозрачно;
- backend предотвращает явные дубли и некорректные назначения.

### 11.6. Gate to next phase

Переход дальше возможен, если:

- доступы и роли можно управлять без ручных обходов;
- account-role contract стабилен;
- UI понимает, как визуализировать права и доступы.

---

## 12. Phase 6 — Process Visibility Layer

### 12.1. Цель

Добавить process-visible слой для запуска и наблюдения onboarding-процесса.

### 12.2. Backend scope

- onboarding runs model;
- run statuses;
- run steps or stage states;
- result/error payloads;
- endpoints для list/detail/status retrieval;
- базовая диагностика ошибок процесса.

### 12.3. Frontend scope

- onboarding runs list;
- run detail page;
- прогресс, статус, ошибки, частичные результаты;
- визуальный контур состояния процесса.

### 12.4. Зачем нужна отдельная фаза до wizard

Потому что wizard без process visibility превращается в «чёрный ящик». Сначала система должна научиться показывать сам процесс и его результаты, и только потом — красиво запускать его из мастера.

### 12.5. Demo milestone

- можно увидеть список runs;
- можно открыть run;
- видно, завершился он успешно или с ошибкой;
- есть базовое объяснение результата.

### 12.6. Gate to next phase

Переход дальше возможен, если:

- процессный слой уже наблюдаем;
- orchestration backend способен возвращать диагностируемый результат;
- UI может отличить running, failed и completed состояния.

---

## 13. Phase 7 — Bootstrap Orchestration Layer

### 13.1. Цель

Собрать главный сценарий продукта: управляемый запуск one-click onboarding через orchestration command + wizard UI.

### 13.2. Backend scope

- bootstrap/orchestration command endpoint;
- orchestration service;
- идемпотентность, где это нужно;
- командная валидация;
- запуск onboarding run;
- возврат run/result contract;
- частичная обработка ошибок и статусных исходов.

### 13.3. Frontend scope

- wizard shell;
- step forms;
- draft state;
- review step;
- submit orchestration command;
- success/failure summary;
- переход к run detail.

### 13.4. На что обратить внимание

Эта фаза должна опираться на уже стабилизированные:

- org structure contracts;
- staffing contracts;
- account-role contracts;
- onboarding run contracts.

Если хотя бы один из этих слоёв ещё нестабилен, wizard быстро превратится в дорогую точку постоянных переделок.

### 13.5. Demo milestone

Главный demo-сценарий MVP:

- пользователь проходит мастер;
- запускает onboarding;
- система создаёт run;
- пользователь видит результат и созданные сущности.

### 13.6. Gate to next phase

Переход дальше возможен, если:

- happy path проходит от начала до конца;
- основные ошибки возвращаются диагностируемо;
- orchestration contract перестаёт меняться хаотично.

## 14. Phase 8 — Hardening and Pilot Stabilization

### 14.1. Цель

Довести систему до состояния управляемого MVP/pilot use.

### 14.2. Backend scope

- contract cleanup;
- error model stabilization;
- migration cleanup;
- guard rails around destructive operations;
- performance sanity checks for list endpoints;
- улучшение observability/logging;
- устранение схемных шероховатостей.

### 14.3. Frontend scope

- polishing empty/loading/error states;
- устранение UX-разрывов;
- stabilizing navigation;
- better feedback after mutations;
- устранение race conditions;
- уточнение текстов, labels и summary blocks;
- accessibility baseline.

### 14.4. Demo milestone

Пилотная демонстрация должна проходить без ручных пояснений на каждом шаге. Пользователь должен видеть логически собранный продукт, а не набор отдельных экранов.

### 14.5. Exit criteria

- основной сценарий проходит сквозным образом;
- ключевые CRUD-разделы стабильны;
- orchestration понятен и диагностируем;
- нет критичных UX/API-разрывов между слоями.

## 15. Инкременты реализации внутри фаз

Внутри каждой фазы желательно работать не абстрактными «большими разделами», а короткими delivery increments.

Рекомендуемый паттерн инкремента:

1. schema / migration;
2. repository;
3. service;
4. router + DTO;
5. API check;
6. frontend integration;
7. acceptance pass;
8. commit.

Это особенно важно для сущностей waves 2–5.

Такой паттерн позволяет:

- быстро локализовать проблемы;
- видеть, на каком слое застряла реализация;
- не смешивать незавершённый backend и незавершённый frontend в один непрозрачный блок изменений.

## 16. Точки фиксации API-контрактов

Контракты не должны считаться стабильными «вообще». У них должны быть конкретные точки фиксации.

### 16.1. Contract Freeze A

После Phase 2:

- list/detail/create/update/delete pattern;
- envelope style;
- validation error format;
- pagination/filter convention.

### 16.2. Contract Freeze B

После Phase 4:

- org unit DTO;
- position DTO;
- employee DTO;
- reference linking conventions.

### 16.3. Contract Freeze C

После Phase 6:

- onboarding run DTO;
- process status model;
- result/error representation.

### 16.4. Contract Freeze D

После Phase 7:

- orchestration command schema;
- orchestration result schema;
- wizard-submit contract.

Именно в этих точках стоит сознательно сокращать произвольные правки API.

---

## 17. Порядок миграций БД

Миграции должны идти не по удобству отдельных разработчиков, а по dependency order.

Рекомендуемый порядок:

1. shared/core baseline tables if needed;
2. reference dictionaries / clients / templates;
3. org units;
4. positions;
5. employees;
6. accounts;
7. account-role assignments;
8. onboarding runs;
9. orchestration-supporting tables / logs if needed;
10. hardening adjustments.

Правило: нельзя мигрировать зависимую сущность раньше, чем зафиксирован её опорный слой.

---

## 18. Порядок реальных интеграций frontend ↔ backend

Практически интеграцию лучше вести так:

### 18.1. Сначала backend endpoint contract + manual API check

До подключения UI желательно проверить endpoint руками или contract tests.

### 18.2. Затем frontend list/detail integration

Сначала чтение, потом только mutation UI.

### 18.3. Затем create/update integration

После подтверждения чтения и отображения.

### 18.4. Затем delete/deactivate flow

Разрушительные операции подключать последними.

### 18.5. Затем polish and acceptance

Каждый раздел должен завершаться коротким acceptance-pass.

Это снижает риск того, что UI маскирует backend-проблему или наоборот.

## 20. Критерии перехода между фазами

Каждая следующая фаза должна запускаться не по календарю, а по критериям готовности.

### 20.1. Минимальный принцип

Следующая фаза начинается, если:

- текущий слой демонстрируем;
- его контракты достаточно стабильны;
- команда понимает, что reuse-паттерн уже сложился;
- нет открытой критичной схемной неопределённости.

### 20.2. Что не считается готовностью

Не считается готовностью:

- «backend почти сделан»;
- «frontend пока на моках»;
- «wizard нарисован, но process contract ещё меняется»;
- «списки есть, но create/update/delete ещё нестабильны».

Готовность — это не количество написанного кода, а наличие устойчивого рабочего слоя.

## 21. Рекомендуемый порядок коммитов и интеграций

Коммиты лучше вести так, чтобы история отражала delivery sequence.

Примерно:

1. chore: project foundation and shared conventions
2. feat(api): baseline reference contracts
3. feat(backend): first reference crud slice
4. feat(frontend): first reference crud ui slice
5. feat(backend): org units slice
6. feat(frontend): org units workspace
7. feat(backend): positions and employees slices
8. feat(frontend): staffing ui slices
9. feat(backend): accounts and role assignments
10. feat(frontend): accounts and roles ui
11. feat(backend): onboarding runs and process state
12. feat(frontend): onboarding runs ui
13. feat(backend): bootstrap orchestration

Это даёт:

- понятную историю проекта;
- меньший риск конфликтов;
- удобную привязку к demo milestones.

## 22. Риски неправильной последовательности

Ниже — типовые sequencing risks.

### 22.1. Слишком ранний wizard

Результат:

- постоянные переделки шагов;
- смена payload contract;
- потеря доверия к UI.

### 22.2. Слишком ранний access layer

Результат:

- роли цепляются к нестабильным сущностям;
- начинают ломаться связи employee/account/position.

### 22.3. Слишком поздняя process visibility

Результат:

- orchestration не наблюдаем;
- ошибки процесса непонятны;
- wizard превращается в непрозрачную кнопку.

### 22.4. Слабая фиксация DTO

Результат:

- frontend пишет page-level mapping хаотично;
- backend меняет названия и shape полей без дисциплины;
- интеграция дорожает.

### 22.5. Несистемные миграции

Результат:

- rollback сложен;
- зависящие таблицы приходится переделывать повторно;
- dev/test среда начинает расходиться.

## 24. Что должно быть готово до старта пилота

До пилотного запуска желательно иметь:

- стабильные CRUD-разделы по ключевым сущностям;
- работающий org structure contour;
- рабочую кадровую основу;
- управляемые роли/аккаунты;
- наблюдаемый onboarding process;
- one-click onboarding happy path;
- базовую диагностику ошибок;
- минимальный smoke test набор.

Если этого нет, проект ещё находится в стадии внутренней реализации, а не в стадии pilot readiness.

## 25. Итоговый practical route

Если упростить весь документ до одной рабочей формулы, она будет такой:

**зафиксировать baseline → собрать foundation → стабилизировать CRUD → собрать оргструктуру → собрать кадровую модель → добавить роли и доступы → сделать процесс наблюдаемым → собрать orchestration wizard → провести hardening.**

Именно в таком порядке проект с высокой вероятностью придёт к устойчивому MVP без лишних архитектурных возвратов.
