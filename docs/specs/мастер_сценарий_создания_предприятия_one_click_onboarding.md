# Мастер-сценарий создания предприятия

## 1. Назначение документа
Данный документ описывает целевой сценарий быстрого создания нового предприятия-заказчика в платформе по принципу **one-click onboarding** или «создание предприятия одной кнопкой».

Документ нужен для того, чтобы связать между собой:
- бизнес-логику запуска нового B2B-заказчика;
- архитектурную концепцию платформы;
- концептуальную модель данных;
- будущую реализацию backend workflow;
- будущую реализацию UI-мастера;
- будущие API-методы создания и развёртывания предприятия.

По сути, это переход от уровня «что должна уметь система» к уровню «как именно она должна это делать».

---

## 2. Цель сценария
Цель мастер-сценария — обеспечить максимально быстрый, стандартизированный и контролируемый запуск нового корпоративного заказчика, при котором:
- создаётся новый заказчик как юридическое лицо;
- автоматически создаётся базовая организационная структура;
- автоматически создаются типовые подразделения и должности;
- создаётся стартовая административная учётная запись;
- назначаются базовые роли и права;
- система подготавливает предприятие к вводу сотрудников и подключению прикладных модулей.

Итог сценария: вместо длительного ручного построения инфраструктуры пользователь получает уже развёрнутый каркас предприятия, который можно сразу донастроить и использовать.

---

## 3. Общая идея сценария

### 3.1. Что означает «одной кнопкой»
Под «одной кнопкой» здесь не следует понимать полное отсутствие входных данных. Практически это означает:
- один мастер-процесс в интерфейсе;
- единая точка входа в создание предприятия;
- последовательное выполнение автоматизированных шагов без ручного перехода между разрозненными разделами;
- получение предсказуемого и целостного результата.

### 3.2. Принцип работы
Пользователь не создаёт по отдельности:
- компанию;
- потом подразделения;
- потом должности;
- потом роли;
- потом администратора.

Вместо этого он запускает единый сценарий, а система сама создаёт необходимый стартовый набор сущностей по выбранному шаблону.

---

## 4. Участники сценария

## 4.1. Основной инициатор
### Платформенный администратор
Имеет право создавать новых заказчиков и запускать сценарий развёртывания.

## 4.2. Дополнительные участники
### Оператор внедрения
Может запускать развёртывание, если ему даны соответствующие права.

### Системный администратор заказчика
Не обязательно инициирует развёртывание, но может быть создан в ходе сценария и затем принимать результат.

---

## 5. Предусловия сценария
Перед запуском должны выполняться базовые условия:
- пользователь аутентифицирован;
- пользователь имеет право на создание нового заказчика;
- в системе существует хотя бы один активный шаблон предприятия;
- в системе настроены базовые справочники типов оргединиц и ролей;
- инфраструктурные модули платформы доступны и не заблокированы.

Если одно из условий не выполнено, сценарий не должен запускаться.

---

## 6. Входные данные мастер-сценария

Ниже приведён минимальный набор входных параметров.

## 6.1. Обязательные поля
- название заказчика;
- краткое название заказчика — при необходимости;
- отраслевой профиль или тип бизнеса;
- выбранный шаблон предприятия;
- данные стартового администратора;
- базовый язык / locale;
- часовой пояс — при необходимости.

## 6.2. Данные стартового администратора
Минимально:
- ФИО;
- логин;
- email или телефон;
- способ задания первого пароля:
  - система генерирует временный пароль;
  - оператор задаёт временный пароль;
  - отправляется приглашение.

## 6.3. Опциональные параметры
- БИН / регистрационный номер;
- город / регион;
- комментарий к внедрению;
- перечень активируемых прикладных модулей;
- признак немедленного создания типовых сотрудников или только структуры;
- выбор расширенных подразделений, если шаблон их допускает.

---

## 7. Результаты сценария

После успешного завершения сценария в системе должны существовать:
- карточка заказчика;
- профиль заказчика;
- корневой узел оргструктуры;
- набор типовых подразделений;
- при необходимости — вложенные сектора и секции;
- набор типовых должностей;
- стартовая административная учётная запись;
- базовые ролевые назначения;
- запись о запуске развёртывания;
- журнал шагов сценария.

После этого пользователь должен попасть в экран пост-настройки, где можно:
- отредактировать оргструктуру;
- добавить сотрудников;
- импортировать сотрудников;
- скорректировать должности;
- назначить роли;
- активировать прикладные модули.

---

## 8. Основной поток сценария

Ниже описан целевой поток выполнения.

## Шаг 1. Открытие мастера создания предприятия
Платформенный администратор открывает интерфейс «Создать предприятие».

### Система должна:
- показать форму ввода основных параметров;
- загрузить список доступных шаблонов;
- показать краткое описание выбранного шаблона;
- при необходимости показать набор модулей, доступных для подключения.

---

## Шаг 2. Ввод основных данных заказчика
Пользователь вводит данные юридического лица и выбирает шаблон.

### Система должна проверить:
- заполненность обязательных полей;
- уникальность внутреннего кода заказчика, если код задаётся вручную;
- допустимость выбранного шаблона;
- корректность формата email / логина стартового администратора;
- отсутствие недопустимого конфликта по логину.

### Возможные ошибки
- не заполнено обязательное поле;
- шаблон недоступен;
- логин уже существует;
- некорректный email;
- недопустимый формат кода заказчика.

---

## Шаг 3. Создание карточки заказчика
После успешной валидации система создаёт сущность заказчика.

### Создаётся
- CustomerCompany;
- CustomerProfile;
- при необходимости — CustomerModuleActivation для базовых модулей.

### Что важно
На этом этапе создаётся tenant-контур, с которым будут связаны все последующие сущности.

---

## Шаг 4. Создание корневого узла оргструктуры
Система создаёт корневую организационную единицу заказчика.

### Обычно это
- компания;
- головная организация;
- основной узел дерева оргструктуры.

### Создаётся
- корневой OrgUnit с типом `company`.

### Что важно
Все дальнейшие подразделения должны быть развёрнуты как дочерние или вложенные узлы по отношению к корню.

---

## Шаг 5. Развёртывание оргструктуры по шаблону
Система берёт выбранный шаблон предприятия и создаёт набор шаблонных оргединиц.

### Пример для типового шаблона
Создаются:
- администрация;
- отдел кадров;
- отдел маркетинга;
- бухгалтерия;
- производственный отдел.

При расширенном шаблоне могут дополнительно создаваться:
- контроль качества;
- отдел расширения бизнеса.

### Для мебельной компании могут создаваться вложенные узлы
В производственном блоке:
- сектор планирования производства;
- сектор комплектования;
- сектор производства мебели.

### Создаётся
- набор OrgUnit на основании TemplateOrgUnit.

### Bundle шаблона (template_code)
Код шаблона (`EnterpriseTemplate.code`) — ключ изоляции для всего нормативного набора:
- `template_org_units` — дерево подразделений;
- `position_catalog` + `position_dept_types` — должности и привязки к типам отделений;
- `kpi_templates` — типовые KPI;
- `position_regulations` + `regulation_kpis` + `regulation_instructions` — регламенты;
- `sa_competency_catalog_versions` + `sa_competency_matrix` + `sa_competency_skill_definitions` — матрица навыков.

При onboarding и deploy-template система резолвит `template_code` через `Client.template_id` и разворачивает только записи выбранного bundle, а не глобальный каталог целиком.

Клонирование bundle (`POST /api/enterprise-templates/{id}/clone`) создаёт новый черновой шаблон с копией всех слоёв; опциональный `code_prefix` добавляет префикс к кодам узлов/должностей для читаемости в сводных отчётах.

### Требования
- должна соблюдаться иерархия;
- должны сохраняться связи parent-child;
- должны сохраняться коды и порядок сортировки;
- автосозданные узлы должны иметь признак системного происхождения.

---

## Шаг 6. Развёртывание должностей
После создания оргструктуры система создаёт типовые должности.

### Примеры должностей
- директор;
- системный администратор;
- руководитель отдела кадров;
- бухгалтер;
- маркетолог;
- начальник производства;
- специалист по качеству;
- менеджер по развитию.

### Создаётся
- Position;
- OrgUnitPositionBinding.

### Требования
- должности должны создаваться в правильном контексте подразделений;
- должна поддерживаться возможность одинаковых должностей в разных подразделениях;
- должен сохраняться признак обязательности / типового происхождения.

---

## Шаг 7. Создание стартовой учётной записи администратора
Система создаёт аккаунт стартового администратора заказчика.

### Возможны варианты
1. создаётся новый Employee + UserAccount;
2. создаётся только UserAccount, а Employee создаётся позже;
3. создаются и Employee, и первичное EmploymentAssignment в подразделение «Администрация».

### Предварительная рекомендация
Для практической целостности лучше сразу создавать:
- Employee;
- UserAccount;
- EmploymentAssignment;
- UserRoleAssignment.

Это позволяет администратору сразу существовать и как пользователю, и как сотруднику организационной модели.

### Требования
- логин должен быть уникальным;
- пароль должен удовлетворять политике безопасности;
- аккаунт должен иметь понятный стартовый статус;
- должен быть определён механизм первого входа.

---

## Шаг 8. Назначение стартовых ролей и прав
После создания администратора система назначает ему роль в рамках нового заказчика.

### Как минимум
- CUSTOMER_SYS_ADMIN.

### При необходимости дополнительно
- IMPLEMENTATION_OPERATOR;
- ORG_HEAD для определённого подразделения;
- доступ к модулям, включённым на старте.

### Создаётся
- UserRoleAssignment;
- AccessScope.

### Требования
- роль должна быть ограничена контуром данного заказчика;
- нельзя случайно дать межклиентский доступ;
- при наличии оргконтекста он должен быть задан явно.

---

## Шаг 9. Фиксация результата развёртывания
Система завершает run развёртывания и фиксирует его статус.

### Создаётся / обновляется
- DeploymentRun;
- DeploymentStep;
- AuditLog.

### Итоговый статус
- completed — полностью успешно;
- partial — создано частично, требуется ручная доработка;
- failed — сценарий не завершён.

---

## Шаг 10. Переход к пост-настройке
После завершения мастер-сценария пользователь должен быть переведён в интерфейс донастройки нового предприятия.

### На этом экране должны быть доступны действия
- просмотреть дерево оргструктуры;
- переименовать подразделения;
- удалить ненужные типовые подразделения;
- добавить дополнительные секции;
- просмотреть типовые должности;
- импортировать сотрудников;
- создать первых сотрудников вручную;
- назначить дополнительные роли;
- активировать прикладные модули.

---

## 9. Альтернативные и дополнительные потоки

## 9.1. Создание заказчика без сотрудников
Иногда нужно сначала создать только инфраструктурный каркас.

### В таком случае
- создаётся компания;
- создаётся оргструктура;
- создаются должности;
- создаётся только стартовый админ;
- остальные сотрудники вводятся позже.

Это должен быть основной режим для MVP.

---

## 9.2. Создание заказчика с последующим импортом сотрудников
После завершения мастера пользователь сразу переходит к импорту Excel/CSV.

### Важно
Этот поток не должен быть частью критического пути основного мастер-сценария, иначе ошибки импорта будут ломать процесс создания предприятия.

Лучше:
- сначала завершить развёртывание каркаса;
- потом отдельно выполнять импорт.

---

## 9.3. Развёртывание по упрощённому шаблону
Для некоторых пилотов может быть нужен облегчённый шаблон.

### Пример
Создаются только:
- администрация;
- HR;
- базовый производственный блок;
- системный администратор.

Такой режим полезен для быстрых proof-of-concept.

---

## 9.4. Повторное развёртывание отдельных частей
В некоторых случаях пользователь может захотеть дозагрузить типовые подразделения или типовые должности, которые были пропущены.

### Это означает
Система должна поддерживать не только полный первичный run, но и контролируемые повторные операции:
- добавить типовые подразделения;
- добавить типовые должности;
- добавить шаблонные роли.

Это особенно важно для идемпотентности и безопасного восстановления после частичного сбоя.

---

## 10. Валидации и проверки

## 10.1. Бизнес-валидации
Перед запуском и в ходе сценария должны проверяться:
- право пользователя на создание заказчика;
- существование шаблона;
- допустимость шаблона для выбранного режима;
- уникальность логина стартового администратора;
- корректность tenant-контекста;
- отсутствие дублирующего заказчика по внутреннему коду — если это правило вводится.

## 10.2. Технические проверки
Также необходимо проверять:
- наличие обязательных справочников;
- наличие системных ролей;
- доступность БД;
- возможность записи всех обязательных сущностей;
- целостность parent-child связей при создании OrgUnit.

## 10.3. Пост-проверки после завершения
После сценария желательно выполнить автоматическую сверку:
- создан ли CustomerCompany;
- создан ли корневой OrgUnit;
- созданы ли обязательные подразделения;
- создан ли хотя бы один UserAccount администратора;
- назначена ли хотя бы одна административная роль;
- завершён ли DeploymentRun без критических ошибок.

---

## 11. Ошибки и обработка сбоев

## 11.1. Принцип обработки ошибок
Сценарий должен быть управляемым и наблюдаемым. Недостаточно просто вернуть пользователю ошибку. Нужно понимать:
- на каком шаге произошёл сбой;
- что уже успело создаться;
- можно ли повторить шаг;
- нужен ли rollback;
- можно ли завершить сценарий в статусе partial.

## 11.2. Категории ошибок
### Ошибки входных данных
- незаполненные обязательные поля;
- некорректный логин;
- дублирующийся код заказчика;
- шаблон недоступен.

### Ошибки конфигурации платформы
- отсутствует роль CUSTOMER_SYS_ADMIN;
- отсутствуют типы оргединиц;
- шаблон повреждён или неполон.

### Ошибки исполнения
- ошибка записи в БД;
- нарушение ограничений целостности;
- коллизия при создании аккаунта;
- ошибка генерации иерархии.

---

## 11.3. Рекомендуемая стратегия завершения
Нужно различать два режима.

### Режим A. Атомарный запуск
Весь сценарий выполняется в рамках одной большой транзакции.

#### Плюсы
- высокая целостность;
- нет «половинчатых» заказчиков.

#### Минусы
- при длинном сценарии и расширении функционала это может стать тяжёлым и неудобным.

### Режим B. Оркестрация шагов с журналированием
Каждый шаг фиксируется отдельно, а система умеет отмечать run как partial или failed.

#### Плюсы
- лучше подходит для реальной платформы;
- можно повторять отдельные шаги;
- выше наблюдаемость.

#### Предварительная рекомендация
Для вашей платформы рациональнее ориентироваться на **оркестрируемый сценарий с шагами и журналом**, а не на одну огромную транзакцию.

При этом внутри отдельных шагов транзакции всё равно нужны.

---

## 12. Идемпотентность и повторный запуск

Для сценария развёртывания это критически важный аспект.

## 12.1. Почему это важно
Если на шаге 7 произошёл сбой, нельзя требовать от пользователя полностью пересоздавать предприятие вручную.

## 12.2. Что желательно обеспечить
- повторный запуск без дублирования уже созданных обязательных сущностей;
- пропуск успешно завершённых шагов;
- возможность дозагрузки типовых блоков;
- журнал того, что было создано автоматически.

## 12.3. Практический принцип
У автосозданных сущностей должны быть признаки происхождения:
- создано по шаблону;
- создано каким шаблоном;
- создано в каком deployment run.

Это облегчит:
- повторный запуск;
- сверку;
- возможный частичный rollback;
- аудит изменений.

---

## 13. Требования к пользовательскому интерфейсу мастера

## 13.1. Форма должна быть короткой
На первом экране не должно быть слишком много полей. Иначе теряется сама идея быстрого запуска.

## 13.2. Пользователь должен понимать последствия выбора шаблона
Желательно сразу показывать:
- какие подразделения будут созданы;
- какие должности будут добавлены;
- какие модули доступны.

## 13.3. После выполнения нужен понятный итоговый экран
Пользователь должен видеть:
- что создано;
- что требует внимания;
- куда перейти дальше.

## 13.4. Нужен переход к следующим операциям
После создания предприятия UI должен вести пользователя дальше:
- в оргструктуру;
- в сотрудников;
- в импорт;
- в роли и доступы.

## 14. Требования к backend workflow

На уровне backend мастер-сценарий должен быть реализован как управляемый orchestration flow.

## 14.1. Желательная внутренняя декомпозиция шагов
- validate_request;
- create_customer;
- create_customer_profile;
- create_root_org_unit;
- deploy_org_units;
- deploy_positions;
- create_admin_employee;
- create_admin_account;
- assign_admin_role;
- finalize_run.

## 14.2. Требования к реализации
- каждый шаг должен быть логируемым;
- каждый шаг должен иметь код статуса;
- должен быть понятен результат и ошибка шага;
- шаги должны иметь возможность повторного запуска при безопасных условиях;
- весь run должен иметь уникальный идентификатор.

## 15. Черновая структура API для сценария

На данном этапе это только проектная наметка.

### Возможные endpoint’ы
- `POST /customers/onboarding-runs` — создать новый run развёртывания;
- `GET /customers/onboarding-runs/{id}` — получить статус run;
- `POST /customers/onboarding-runs/{id}/retry` — повторить неуспешный run или отдельные шаги;
- `GET /enterprise-templates` — список шаблонов;
- `GET /enterprise-templates/{id}/structure-preview` — preview bundle (оргструктура, должности, KPI, регламенты, навыки);
- `PATCH /enterprise-templates/{id}` — свойства шаблона (название, версия, описание);
- `POST /enterprise-templates/{id}/clone` — клонирование изолированного bundle;
- `GET /enterprise-templates/{id}/preview` — preview того, что будет создано;
- `POST /customers/{id}/org-structure/bootstrap-missing` — дозагрузить недостающие типовые блоки.

### Для MVP
Можно начать с более простого варианта:
- `POST /customers/bootstrap`
- `GET /customers/{id}`
- `GET /customers/{id}/org-units`
- `GET /customers/{id}/positions`
- `GET /customers/{id}/deployment-runs`

## 16. Минимальный целевой сценарий для MVP

Чтобы не перегружать первую реализацию, для MVP можно зафиксировать упрощённый вариант.

## MVP-поток
1. Пользователь вводит название заказчика.
2. Выбирает один из 2–3 шаблонов.
3. Указывает данные стартового администратора.
4. Система создаёт заказчика.
5. Система создаёт корневой узел и набор типовых подразделений.
6. Система создаёт набор типовых должностей.
7. Система создаёт администратора и назначает роль CUSTOMER_SYS_ADMIN.
8. Пользователь попадает на экран редактирования структуры.

### Что можно отложить
- сложные режимы повторного запуска;
- расширенную модульную активацию;
- сложные сценарии частичного rollback;
- автоматическое создание большого числа типовых сотрудников;
- интеграции с внешними HR-источниками.

---

## 17. Критерии успешности сценария

Сценарий считается успешным, если:
- новый заказчик создан;
- существует корневой узел оргструктуры;
- созданы обязательные подразделения по шаблону;
- созданы типовые должности;
- существует активный стартовый администратор;
- администратору назначена административная роль;
- результат отображается в интерфейсе без перехода к ручному созданию сущностей с нуля.

---

## 18. Что даёт этот сценарий в бизнес-практике

Реализация такого мастер-процесса позволит:
- резко сократить время старта нового B2B-заказчика;
- стандартизировать внедрение;
- уменьшить число ручных ошибок;
- быстрее доходить до этапа тестирования новых идей;
- использовать одну и ту же платформу как типовой конструктор корпоративной среды.

Это особенно важно в вашем случае, потому что прикладная ценность системы возникает не на этапе ввода оргструктуры, а на этапе тестирования, диагностики, задач и обучения. Следовательно, всё, что ускоряет инфраструктурное развёртывание, напрямую повышает скорость продуктовых экспериментов.
