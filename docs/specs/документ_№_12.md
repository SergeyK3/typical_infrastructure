# Документ №12. Frontend Screen Map + Navigation Model

## 1. Назначение документа

Frontend Screen Map + Navigation Model фиксирует пользовательскую карту MVP-интерфейса и правила перемещения по нему.

Если предыдущие документы описывали:

- архитектуру системы;
- backend и frontend delivery plans;
- implementation sequence;
- work breakdown;
- iteration plan,

то этот документ отвечает на следующий практический вопрос:

**какие именно экраны должны существовать в MVP, как они связаны между собой, как пользователь перемещается между ними и как сценарии one-click onboarding, управления оргструктурой, должностями, сотрудниками и ролями складываются в единый интерфейсный контур.**

Этот документ нужен, чтобы до начала детальной UI-реализации не осталось разрыва между delivery-планом и реальным поведением пользовательского интерфейса.

---

## 2. Что именно должен зафиксировать этот документ

Документ должен зафиксировать:

- состав экранов MVP;
- тип каждого экрана;
- логику primary navigation;
- логику secondary navigation;
- связи между списками, карточками, рабочими пространствами и wizard-сценариями;
- переходы между связанными сущностями;
- обязательные состояния экранов;
- минимальные правила breadcrumb и back-navigation;
- ключевые UX-маршруты пользователя.

Иными словами, это экранная и навигационная модель MVP, а не просто перечень страниц.

---

## 3. Базовый принцип screen map

Экранная карта должна строиться не от таблиц базы данных, а от пользовательских действий.

Пользователь мыслит не так:

- открыть clients table;
- открыть positions table;
- открыть employees table.

Он мыслит так:

- завести заказчика;
- описать структуру предприятия;
- задать должности;
- ввести сотрудников;
- назначить роли и доступы;
- запустить onboarding;
- просмотреть результат.

Поэтому screen map должна поддерживать именно этот сценарный способ мышления.

---

## 4. Основные типы экранов в MVP

Для MVP рекомендуется использовать ограниченный и понятный набор типов экранов.

### 4.1. Landing / Dashboard Screen

Экран входа в рабочее пространство системы.

### 4.2. List Screen

Экран списка сущностей с фильтрами, поиском и действиями первого уровня.

### 4.3. Detail / Edit Screen

Экран карточки сущности или редактирования сущности.

### 4.4. Workspace Screen

Экран для работы со структурой или составной сущностью, например:

- org units hierarchy;
- accounts and roles workspace.

### 4.5. Wizard Screen

Пошаговый сценарный экран для one-click onboarding.

### 4.6. Process Monitoring Screen

Экран просмотра onboarding run и его результата.

### 4.7. System / Utility Screen

Экран служебного или административного назначения:

- access denied;
- not found;
- diagnostics;
- health/admin pages, если они входят в MVP.

Ограничение числа типов экранов помогает удерживать интерфейс консистентным.

---

## 5. Верхнеуровневая навигационная модель

На уровне primary navigation рекомендуется следующая структура разделов MVP:

1. Dashboard
2. Clients
3. Organization
4. Positions
5. Employees
6. Accounts & Roles
7. Onboarding Runs
8. Onboarding Wizard
9. Admin / System (если нужен в MVP)

Это означает, что primary navigation строится вокруг предметных рабочих зон, а не вокруг технических слоёв.

---

## 6. Рекомендуемая структура primary navigation

### 6.1. Dashboard

Назначение:

- точка входа;
- быстрый доступ к основным действиям;
- обзор последних или ключевых сущностей, если это нужно в MVP.

### 6.2. Clients

Назначение:

- список заказчиков/юридических лиц;
- вход в клиентский контур;
- старт сценария создания и редактирования клиента.

### 6.3. Organization

Назначение:

- управление оргструктурой;
- визуальная работа с подразделениями;
- переход к связанным позициям и staffing-слою.

### 6.4. Positions

Назначение:

- управление должностями;
- фильтрация по клиенту/подразделению;
- вход в staffing-базу.

### 6.5. Employees

Назначение:

- управление сотрудниками;
- просмотр кадровых привязок;
- переход к аккаунтам и ролям.

### 6.6. Accounts & Roles

Назначение:

- управление системными аккаунтами;
- назначение ролей;
- просмотр access model.

### 6.7. Onboarding Runs

Назначение:

- просмотр history и статусов запусков;
- наблюдение процесса;
- диагностика результатов и ошибок.

### 6.8. Onboarding Wizard

Назначение:

- главный сценарный вход в one-click onboarding.

### 6.9. Admin / System

Назначение:

- служебные системные страницы, если они действительно входят в MVP.

## 8. Экранная модель по разделам

## 8.1. Dashboard

### Экран

**S02. Dashboard**

### Тип

Landing / Dashboard Screen

### Основное назначение

- дать пользователю понятную точку входа;
- показать основные рабочие зоны;
- предложить основные действия первого уровня.

### Минимальный состав блоков

- quick actions;
- recent onboarding runs;
- shortcut to create client;
- shortcut to onboarding wizard.

### Основные переходы

- в Clients List;
- в Onboarding Wizard;
- в Onboarding Runs List;
- при необходимости — в Organization workspace конкретного клиента.

### Замечание

Dashboard в MVP не должен пытаться быть BI-панелью. Его задача — ориентировать пользователя и ускорять старт сценариев.

---

## 8.2. Clients section

### S10. Clients List

Тип: List Screen

Назначение:

- список клиентов;
- поиск/фильтрация;
- вход в клиентский контур.

Основные действия:

- create client;
- open client detail;
- перейти к organization клиента;
- перейти к onboarding wizard для выбранного клиента.

### S11. Client Create

Тип: Detail / Edit Screen

Назначение:

- создание нового клиента.

Основные действия:

- заполнить client basics;
- сохранить;
- перейти в Client Detail или в следующий связанный сценарий.

### S12. Client Detail / Edit

Тип: Detail / Edit Screen

Назначение:

- просмотр и редактирование клиента;
- точка перехода в связанные разделы.

Основные переходы:

- в Org Units Workspace по клиенту;
- в Positions List с фильтром по клиенту;
- в Employees List с фильтром по клиенту;
- в Accounts & Roles с фильтром по клиенту, если применимо;
- в Onboarding Runs List по клиенту;
- в Onboarding Wizard с предзаполненным контекстом клиента.

### Ключевое правило

Карточка клиента должна быть не тупиком, а навигационным узлом в связанный пользовательский контур.

---

## 8.3. Organization section

### S20. Org Units Workspace

Тип: Workspace Screen

Назначение:

- управление оргструктурой клиента;
- работа с иерархией подразделений.

Основные блоки:

- hierarchy panel/tree;
- details panel или contextual actions;
- create/edit controls;
- breadcrumbs/path to node.

Основные действия:

- create root unit;
- create child unit;
- edit unit;
- activate/deactivate unit;
- перейти к positions по выбранному подразделению;
- перейти к employees по выбранному подразделению.

### S21. Org Unit Create / Edit

Тип: Modal / Pane / Detail Editor

Назначение:

- создание и редактирование отдельного узла оргструктуры.

### Ключевое правило

Org Units Workspace должен быть полноценной рабочей зоной, а не просто плоским списком с parent_id.

---

## 8.4. Positions section

### S30. Positions List

Тип: List Screen

Назначение:

- просмотр и фильтрация должностей.

Основные фильтры:

- client;
- org unit;
- active status.

Основные действия:

- create position;
- open detail/edit;
- перейти к employees, связанным с позицией, если это входит в MVP.

### S31. Position Create

Тип: Detail / Edit Screen

Назначение:

- создание должности с привязкой к org unit.

### S32. Position Detail / Edit

Тип: Detail / Edit Screen

Назначение:

- просмотр и редактирование должности;
- переходы в кадровый контур.

Основные переходы:

- в Org Units Workspace на связанный узел;
- в Employees List с фильтром по должности.

### Ключевое правило

Раздел должностей должен быть связан с оргструктурой явно, а не существовать как изолированный каталог.

---

## 8.5. Employees section

### S40. Employees List

Тип: List Screen

Назначение:

- список сотрудников;
- поиск и фильтрация;
- вход в кадровый контур.

Основные фильтры:

- client;
- org unit;
- position;
- active status.

Основные действия:

- create employee;
- open employee detail;
- перейти к account/roles для сотрудника.

### S41. Employee Create

Тип: Detail / Edit Screen

Назначение:

- создание кадровой записи сотрудника.

### S42. Employee Detail / Edit

Тип: Detail / Edit Screen

Назначение:

- просмотр и редактирование сотрудника;
- отображение связей с org unit, position и account.

Основные переходы:

- в Org Units Workspace на подразделение сотрудника;
- в Position Detail на должность сотрудника;
- в Account Detail / Role Assignment для связанного аккаунта.

### Ключевое правило

Карточка сотрудника должна явно показывать различие между employee, position и account, чтобы пользователь не путал кадровую сущность с учётной записью.

---

## 8.6. Accounts & Roles section

### S50. Accounts List

Тип: List Screen

Назначение:

- список аккаунтов;
- вход в access-layer.

Основные действия:

- open account detail;
- создать аккаунт или связать аккаунт с employee, если это поддержано;
- перейти к role assignments.

### S51. Account Detail / Edit

Тип: Detail / Edit Screen

Назначение:

- просмотр и редактирование аккаунта;
- показ связанного сотрудника;
- показ ролей.

### S52. Role Assignment Workspace / Panel

Тип: Workspace / Embedded Panel

Назначение:

- назначение и отзыв ролей;
- визуализация access model.

Основные действия:

- assign role;
- revoke/deactivate role;
- просмотреть активные назначения;
- при необходимости перейти к employee detail.

### Ключевое правило

Раздел аккаунтов и ролей должен быть понятен с точки зрения пользователя: либо как управление доступами сотрудника, либо как управление ролями аккаунта. Не нужно смешивать обе модели без явной UX-логики.

---

## 8.7. Onboarding Runs section

### S60. Onboarding Runs List

Тип: Process Monitoring Screen / List Screen

Назначение:

- список запусков onboarding;
- фильтры по статусу, клиенту, времени;
- вход в наблюдение процесса.

Основные действия:

- открыть run detail;
- перейти к связанному клиенту;
- перейти к wizard context, если нужен повторный запуск.

### S61. Onboarding Run Detail

Тип: Process Monitoring Screen

Назначение:

- показать статус процесса;
- показать шаги/stages;
- показать ошибки;
- показать частичный или полный результат.

Основные блоки:

- run summary;
- status badge;
- step/stage timeline;
- errors and diagnostics;
- created entities summary.

### Ключевое правило

Run detail должен объяснять пользователю, что произошло, а не просто показывать machine status.

---

## 8.8. Onboarding Wizard section

### S62. Onboarding Wizard

Тип: Wizard Screen

Назначение:

- главный сценарий one-click onboarding.

Рекомендуемые шаги:

1. Client Basics
2. Organization Setup
3. Positions / Templates
4. Employees / Accounts / Roles
5. Review
6. Run and Result

Точная структура зависит от итогового orchestration contract.

Основные действия:

- перемещение между шагами;
- сохранение draft state;
- review;
- submit orchestration command;
- переход к run detail или result summary.

### S63. Onboarding Result Summary

Тип: Process Summary Screen или финальный шаг Wizard

Назначение:

- человекочитаемый итог запуска;
- ссылка на run detail;
- ссылка на созданные сущности.

### Ключевое правило

Wizard не должен дублировать все рабочие разделы. Он должен собирать сценарий первичного запуска. Для детальной донастройки пользователь дальше уходит в обычные разделы: organization, positions, employees, accounts.

## 9. Связи между экранами

Ниже — рекомендованная логика основных переходов.

### 9.1. Клиент как навигационный узел

Из Client Detail пользователь должен иметь быстрый переход в:

- Org Units Workspace;
- Positions List;
- Employees List;
- Accounts & Roles;
- Onboarding Runs;
- Onboarding Wizard.

### 9.2. Org unit как связующий узел между organization и staffing

Из выбранного org unit должны быть доступны переходы в:

- Positions filtered by org unit;
- Employees filtered by org unit.

### 9.3. Position как переход к кадровому контексту

Из Position Detail должны быть доступны переходы в:

- parent org unit;
- employees filtered by position.

### 9.4. Employee как переход к access layer

Из Employee Detail должны быть доступны переходы в:

- org unit;
- position;
- account/roles.

### 9.5. Wizard как сценарный shortcut, а не единственная точка работы

Из Wizard Result пользователь должен иметь переходы в:

- Onboarding Run Detail;
- Client Detail;
- Org Units Workspace;
- Accounts & Roles, если процесс создал доступы.

## 11. Breadcrumb model

Рекомендуется простая и предсказуемая breadcrumb-модель.

Примеры:

- Dashboard / Clients
- Dashboard / Clients / [Client Name]
- Dashboard / Clients / [Client Name] / Organization
- Dashboard / Positions / [Position Name]
- Dashboard / Employees / [Employee Name]
- Dashboard / Onboarding Runs / [Run ID or Human-readable label]
- Dashboard / Onboarding Wizard

### Правило

Breadcrumb должен показывать логический пользовательский контекст, а не технический URL-path.

## 12. Back-navigation policy

Нужно заранее зафиксировать базовые правила «назад».

### 12.1. Из Detail в List

Пользователь возвращается в тот список, откуда пришёл, по возможности с сохранением фильтров.

### 12.2. Из связанного перехода — назад в контекст

Если пользователь пришёл, например, из Client Detail в Organization Workspace, возврат должен сохранять клиентский контекст.

### 12.3. Wizard не должен терять draft state

Назад внутри wizard — это переход по шагам, а не полный выход из сценария с потерей данных.

---

## 13. Screen states, обязательные для MVP

Каждый значимый экран должен иметь минимум следующие состояния.

### 13.1. Initial loading

Экран показывает, что данные загружаются.

### 13.2. Empty state

Если данных нет, пользователь должен видеть:

- что здесь пока пусто;
- что можно сделать дальше;
- кнопку основного действия.

### 13.3. Error state

Если загрузка провалилась или операция не удалась, экран должен показать:

- понятное сообщение;
- действие повторной попытки, если это уместно;
- сохранение пользовательского контекста по возможности.

### 13.4. Success feedback state

После create/update/delete пользователь должен понимать, что операция завершилась успешно.

### 13.5. Access denied / unavailable state

Если раздел недоступен, это должно отображаться отдельным системным экраном или встроенным guard state.

## 16. Что не должно происходить в навигационной модели

### 16.1. Не должно быть изолированных тупиковых карточек

Каждая ключевая сущность должна вести в связанный рабочий контур.

### 16.2. Wizard не должен заменять operational UI

Wizard — это сценарий первичного запуска, а не единственный способ управлять сущностями.

### 16.3. Нельзя дублировать одну и ту же рабочую логику в нескольких экранах без причины

Например, полное управление оргструктурой не должно одновременно жить и в wizard, и в отдельном workspace как два конкурирующих интерфейса.

### 16.4. Пользователь не должен терять клиентский контекст при переходах

Особенно в маршрутах client → organization → positions → employees.

---

## 17. Приоритет реализации экранов

Экранная карта не означает, что всё нужно реализовывать сразу.

Рекомендуемый порядок UI-реализации:

1. Dashboard + app shell baseline;
2. Clients List / Create / Detail;
3. первый эталонный CRUD screen;
4. Org Units Workspace;
5. Positions screens;
6. Employees screens;
7. Accounts & Roles screens;
8. Runs List / Run Detail;
9. Onboarding Wizard.

Это соответствует implementation sequence и delivery plans.

---

## 18. Acceptance criteria для документа

Frontend Screen Map + Navigation Model считается достаточным, если:

- определён минимальный состав экранов MVP;
- для каждого ключевого раздела понятен тип экрана;
- зафиксирована primary navigation;
- зафиксированы связи между связанными сущностями;
- описаны ключевые пользовательские маршруты;
- описаны обязательные screen states;
- breadcrumb и back-navigation не оставлены на импровизацию.

## 19. Практический вывод

После фиксации этого документа delivery-пакет замыкается со стороны пользовательского интерфейса.

Теперь уже есть:

- архитектурная модель;
- delivery plans;
- implementation sequence;
- work breakdown;
- sprint iteration plan;
- screen map and navigation model.

Следующий особенно сильный шаг зависит от того, куда двигаться дальше:

1. если нужен ещё более прикладной уровень проектирования UI — логично сделать **Screen Specifications v1** по ключевым экранам;
2. если нужен прямой переход к API-проектированию — логично сделать **OpenAPI Baseline v1 — expanded endpoint contracts**;
3. если нужен более строгий слой данных — логично сделать **MVP Data Dictionary v1**.

Для усиления именно pre-implementation kit наиболее практичным следующим документом обычно становится **MVP Data Dictionary v1**, потому что он окончательно связывает экранную модель, ERD, API-контракты и backend delivery в единый словарь сущностей и полей.
