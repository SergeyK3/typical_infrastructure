# Документ №14. OpenAPI Resource Contracts v1

## 1. Назначение документа

Этот документ фиксирует базовые API-контракты MVP-системы на уровне ресурсов, endpoint-групп, request/response DTO и правил работы с коллекциями.

Его задача — превратить:

- концептуальную модель;
- ERD;
- MVP Data Dictionary;
- Frontend Screen Map;
- Backend Delivery Plan

в практический API-слой, пригодный для согласованной разработки backend и frontend.

Документ не является полной OpenAPI-спецификацией в YAML/JSON формате, но задаёт её канонический каркас и семантику.

---

## 2. Что должен зафиксировать документ

OpenAPI Resource Contracts v1 должен определить:

1. какие API-ресурсы входят в MVP;
2. какие endpoint’ы нужны по каждому ресурсу;
3. какие DTO используются для list/detail/create/update;
4. какие reference DTO используются для селекторов и связей;
5. какие query params допустимы для списков;
6. как выглядят paging, sorting, filtering;
7. как оформляются ошибки;
8. какие поля read-only;
9. какие поля write-only;
10. какие поля обязательны в create/update сценариях;
11. как API-контракт соотносится с экранной моделью.

---

## 3. Базовые принципы API-контракта MVP

Для первой версии рекомендуется следовать следующим принципам:

- REST-like resource model;
- predictable naming;
- единый формат коллекций;
- единый формат ошибок;
- разделение list/detail/create/update DTO;
- минимизация «магических» нестабильных полей;
- отсутствие смешения backend internal model и public API shape.

API должен быть проектирован так, чтобы:

- frontend мог строить экраны без постоянных ad hoc уточнений;
- backend мог стабильно эволюционировать без ломки базовой структуры;
- интеграционный слой мог опираться на устойчивые ресурсы и коды.

---

## 4. Общие правила именования API

Для MVP рекомендуется:

- resource path — plural snake_case или kebab-case;
- field names — snake_case;
- query params — snake_case;
- enum persisted values — lowercase stable codes;
- response envelope — единый по всей системе.

Рекомендуемый стиль path names:

- `/clients`
- `/org-units`
- `/positions`
- `/employees`
- `/accounts`
- `/roles`
- `/account-role-assignments`
- `/onboarding-runs`

Чтобы не дробить стиль, желательно использовать **kebab-case для URL paths** и **snake_case для payload fields**.

Пример:

- path: `/org-units`
- field: `parent_unit_id`

---

## 5. Общий формат коллекций

Для всех list endpoint’ов MVP рекомендуется единый формат:

```json
{
  "items": [...],
  "total": 125,
  "limit": 25,
  "offset": 0
}
```

### Notes

- `items` — массив объектов list DTO;
- `total` — общее число записей после применения фильтра;
- `limit` — размер страницы;
- `offset` — смещение.

Для первого MVP этого достаточно. Cursor-based pagination можно отложить.

---

## 6. Общий формат ошибок

Для всех endpoint’ов желательно использовать единый error shape:

```json
{
  "error": {
    "code": "validation_error",
    "message": "Field 'name' is required",
    "details": {
      "field": "name"
    },
    "request_id": "..."
  }
}
```

### Recommended error fields

- `code` — канонический код ошибки;
- `message` — читаемое сообщение;
- `details` — структурированные детали;
- `request_id` — корреляционный идентификатор запроса.

### Minimal canonical error codes

- `validation_error`
- `not_found`
- `conflict`
- `forbidden`
- `unauthorized`
- `invalid_state`
- `dependency_exists`
- `internal_error`

---

## 7. Общие query conventions

Для list endpoint’ов рекомендуется поддержать:

- `limit`
- `offset`
- `sort_by`
- `sort_order`
- `search`
- resource-specific filters

### Example

`GET /employees?limit=25&offset=0&search=ivan&org_unit_id=12&is_active=true&sort_by=last_name&sort_order=asc`

### Sorting

Рекомендуемые значения:

- `sort_order=asc`
- `sort_order=desc`

Если `sort_by` не передан, используется ресурсный default sort.

---

## 8. DTO layers

Для каждой сущности рекомендуется выделять следующие DTO:

- `ListItem`
- `Detail`
- `CreateRequest`
- `UpdateRequest`
- `Ref`

Иногда дополнительно:

- `CreateResponse`
- `UpdateResponse`
- `FilterSet`
- `LookupItem`

### Принцип

- list DTO — компактный и оптимизированный под таблицы;
- detail DTO — расширенный и пригодный для карточки;
- create/update DTO — только редактируемые поля;
- ref DTO — минимальный объект для селекторов.

### Internal-only fields

- `password_hash`
- internal revision fields
- internal orchestration markers

Frontend не должен зависеть от internal-only fields.

---

## 21. PATCH policy

Для MVP рекомендуется:

- использовать `PATCH` для частичного обновления;
- не требовать полного resend сущности;
- игнорировать отсутствующие поля;
- валидировать только переданные поля плюс их зависимые constraints.

### Example

```json
{
  "name": "New Department Name",
  "is_active": false
}
```

Это особенно важно для модальных редактирований и admin flows.

---

## 22. Relationship expansion policy

Нужно заранее ограничить, что detail endpoint может возвращать вместе с объектом.

Рекомендуется:

- list endpoints не возвращают тяжёлые вложенные объекты;
- detail endpoints могут возвращать limited denormalized helper fields;
- сложные вложенные деревья выносятся в специальные endpoints.

Примеры:

- `/org-units/tree` — для дерева;
- `/onboarding-runs/{id}/items` — для шагов выполнения;
- `/accounts/{id}` — может вернуть `role_codes`, но не полный древовидный RBAC-граф.

---

## 23. Resource-to-screen mapping

Контракты должны напрямую поддерживать экраны MVP.

### Dashboard

Использует summary/orchestration endpoints, не обязательно чистый CRUD.

### Clients

- list → `GET /clients`
- detail → `GET /clients/{id}`
- create → `POST /clients`
- edit → `PATCH /clients/{id}`

### Organization

- tree/list → `GET /org-units`, `GET /org-units/tree`
- detail → `GET /org-units/{id}`
- create/edit → `POST /org-units`, `PATCH /org-units/{id}`

### Positions

- list/detail/create/edit → `/positions`

### Employees

- list/detail/create/edit → `/employees`

### Accounts & Roles

- accounts → `/accounts`
- roles → `/roles`
- role assignments → `/account-role-assignments`

### Onboarding Runs

- list/detail/execute → `/onboarding-runs`

### Onboarding Wizard

- validate/preview/submit → `/onboarding-wizard/*`

---

## 24. Recommended response semantics

### POST create

Рекомендуется возвращать созданный detail object или create response с `id` и минимальным payload.

Практически для MVP лучше возвращать полный detail DTO, чтобы frontend мог сразу обновиться.

### PATCH update

Рекомендуется возвращать актуальный detail DTO после применения изменений.

### DELETE / deactivate

Если удаление разрешено:

- вернуть `204 No Content`

Если используется soft-delete / deactivation:

- вернуть обновлённый detail DTO или `204`, в зависимости от общего стиля API.

---

## 25. Validation and conflict scenarios

Контракт должен заранее учитывать типовые конфликты.

### Examples

- duplicate `code`
- duplicate `login`
- role scope mismatch
- employee and account belong to different client scopes
- parent unit belongs to another client
- account already linked to another employee if such linkage must be unique
- onboarding run cannot be executed from invalid status

### Conflict response example

```json
{
  "error": {
    "code": "conflict",
    "message": "Client code already exists",
    "details": {
      "field": "code",
      "value": "acme"
    },
    "request_id": "..."
  }
}
```

---

## 26. Security-related contract notes

Даже в MVP нужно заранее зафиксировать:

- какие endpoints требуют authentication;
- какие действия требуют elevated permissions;
- какие поля нельзя возвращать обычным пользователям;
- что scope filtering может изменять видимость ресурсов.

OpenAPI Resource Contracts v1 не заменяет RBAC matrix, но должен быть совместим с ней.

Например:

- `/roles` может быть доступен не всем;
- `/accounts/{id}/reset-password` — только admin/super-admin class action;
- `/onboarding-runs/execute` — restricted action.

---

## 27. Versioning policy

Для MVP рекомендуется не усложнять систему ранним URI-versioning, если нет сильной причины.

Допустимые подходы:

- internal versioning by release discipline;
- `/api` prefix without `/v1` for early MVP;
- later explicit `/v1` after contract stabilization.

Если версия включается сразу, она должна быть последовательной:

- `/api/v1/clients`
- `/api/v1/org-units`
- и т.д.

---

## 28. Minimal contract decisions to lock now

До начала реализации желательно зафиксировать следующие решения:

1. точный path style: kebab-case;
2. payload field style: snake_case;
3. collection envelope: `items/total/limit/offset`;
4. patch semantics: partial update only;
5. error envelope: единый;
6. отдельные ref endpoints обязательны;
7. wizard endpoints отделены от CRUD;
8. create/update DTO отделены от detail DTO.

Если это не зафиксировать сейчас, backend и frontend начнут расходиться уже на первых экранах.

---

## 29. Acceptance criteria

Документ можно считать достаточным для MVP, если:

- перечислены все ключевые ресурсы MVP;
- по каждому ресурсу определены базовые endpoint groups;
- описаны list/detail/create/update DTO;
- зафиксирован единый collection envelope;
- зафиксирован единый error envelope;
- определены query/filter conventions;
- определены ref endpoints;
- определены wizard/orchestration endpoints;
- отмечены read-only и write-only поля;
- есть понятная связка с экранной моделью.

---

## 30. Практический вывод

После фиксации OpenAPI Resource Contracts v1 архитектурный пакет становится уже почти достаточным для старта реальной разработки.

Следующий наиболее сильный документ после него — один из двух:

### Вариант A — «Документ №15. RBAC + Permission Matrix v1»

Если следующим приоритетом является стабилизация доступа:

- кто видит какие ресурсы;
- кто может создавать/редактировать/запускать onboarding;
- где нужны admin-only actions.

### Вариант B — «Документ №15. Frontend View Models + UI State Contracts»

Если следующим приоритетом является ускорение frontend delivery:

- table view models;
- form models;
- screen states;
- loading / empty / error semantics.

На практике наиболее системный следующий шаг здесь — **RBAC + Permission Matrix v1**, потому что именно он завершает архитектурную рамку вокруг ресурсов, экранов и backend-контрактов.
