# Документ №6. MVP Backlog by Phases

## 1. Назначение документа

Этот документ переводит архитектурные и API-артефакты проекта в управляемый план MVP-разработки.

Если предыдущие документы отвечали на вопросы:

- **что за продукт мы строим**;
- **какая у него бизнес-логика**;
- **из каких сущностей он состоит**;
- **как проходит one-click onboarding**;
- **через какие endpoint'ы это будет реализовано**,

то данный документ отвечает на вопрос:

**в какой последовательности это разрабатывать, чтобы как можно раньше получить работоспособный MVP без расползания объёма**.

Документ ориентирован на практическую реализацию и нужен как единая основа для:

- backend-планирования;
- frontend-планирования;
- постановки задач по БД;
- проектирования orchestration-логики;
- управления приоритетами MVP.

---

## 2. Базовый принцип фазирования

Для данного проекта наиболее рационален подход не по техническим слоям в отрыве друг от друга, а по **вертикальным инкрементам**.

То есть каждая фаза должна по возможности завершаться не только кодом, но и полезным системным результатом:

- появляется новый рабочий кусок продукта;
- он может быть проверен отдельно;
- он снижает неопределённость для следующей фазы.

Поэтому MVP предлагается строить в пяти фазах:

- **Phase 1 — Foundation & Master Data**
- **Phase 2 — Org Structure & Workforce Core**
- **Phase 3 — Accounts, Roles & Access Readiness**
- **Phase 4 — One-click Onboarding Orchestration**
- **Phase 5 — UI Wizard, Polish & MVP Hardening**

Такой порядок нужен потому, что orchestration нельзя надёжно строить до появления стабильных CRUD-контуров по клиенту, оргструктуре, должностям, сотрудникам и аккаунтам.

---

## 3. Общая логика приоритизации

### В MVP должно войти обязательно

1. Создание заказчика.
2. Выбор шаблона предприятия.
3. Создание оргструктуры.
4. Создание должностей.
5. Создание сотрудников.
6. Создание аккаунтов и назначение ролей.
7. Запуск one-click onboarding.
8. Отслеживание статуса onboarding run.
9. Простой UI-мастер для запуска сценария.

### В MVP не должно разрастись преждевременно

На этом этапе не нужно углубляться в:

- сложную HR-аналитику;
- assessment workflows;
- LMS-интеграции;
- тонкую настройку прав на уровне каждой операции;
- массовый импорт из нескольких источников;
- событийную шину enterprise-уровня;
- продвинутый аудит и версионирование;
- webhooks и внешние callback-механизмы.

Это всё допустимо как следующий этап, но не как условие запуска MVP.

# 4. Phase 1 — Foundation & Master Data

## 4.1. Цель фазы

Создать минимальный системный фундамент, на котором можно безопасно строить дальнейшие сущности и onboarding-flow.

Результат фазы:

- есть базовый API-каркас `/api/v1`;
- есть модель заказчика;
- есть модель шаблона предприятия;
- есть список ролей MVP-уровня;
- есть базовые CRUD/read-контуры для начального справочного слоя;
- есть единый стандарт ответов, ошибок и traceability.

## 4.2. Основной смысл фазы

Phase 1 нужна для того, чтобы убрать архитектурную неопределённость по фундаментальным сущностям. Без этого последующие фазы начинают дублировать контракты, спорить о форматах и ломаться на несовместимых моделях данных.

Именно в этой фазе должны быть зафиксированы:

- naming conventions;
- первичная схема БД;
- правила идентификаторов;
- правила обработки ошибок;
- базовые словари и enum'ы.

## 4.3. Scope фазы

### Backend

Реализовать:

- базовый префикс `/api/v1`;
- health / readiness endpoint, если нужен для dev-цикла;
- `GET /api/v1/roles`;
- `GET /api/v1/enterprise-templates`;
- `GET /api/v1/enterprise-templates/{template_id}`;
- `GET /api/v1/enterprise-templates/{template_id}/structure-preview`;
- `GET /api/v1/clients`;
- `POST /api/v1/clients`;
- `GET /api/v1/clients/{client_id}`;
- `PATCH /api/v1/clients/{client_id}`.

Подготовить:

- базовый error envelope;
- trace_id / request_id propagation;
- базовые Pydantic / DTO схемы;
- базовые service-layer абстракции.

### Database / Model

Создать таблицы или эквивалентные сущности:

- `clients`
- `enterprise_templates`
- `enterprise_template_org_units` или эквивалент для preview
- `enterprise_template_positions` или эквивалент
- `roles`

Минимальные поля:

- идентификатор;
- code;
- name;
- статус / is_active;
- created_at;
- updated_at.

### Frontend

На этом этапе полноценный wizard ещё не обязателен.

Но желательно подготовить:

- каркас раздела администрирования / onboarding;
- экран списка клиентов;
- форму создания клиента;
- экран списка шаблонов;
- экран просмотра preview шаблона.

### Dev / Infra

Подготовить:

- базовую структуру модулей backend;
- окружение dev/stage;
- миграции или baseline schema init;
- seed для ролей и шаблонов;
- единый формат конфигурации.

## 4.4. Endpoint coverage фазы

Фаза закрывает следующие endpoint'ы:

- `GET /api/v1/roles`
- `GET /api/v1/enterprise-templates`
- `GET /api/v1/enterprise-templates/{template_id}`
- `GET /api/v1/enterprise-templates/{template_id}/structure-preview`
- `GET /api/v1/clients`
- `POST /api/v1/clients`
- `GET /api/v1/clients/{client_id}`
- `PATCH /api/v1/clients/{client_id}`

## 4.5. Основные user stories фазы

- Как системный администратор, я хочу видеть доступные шаблоны предприятия, чтобы выбрать основу для нового заказчика.
- Как оператор внедрения, я хочу создать карточку заказчика отдельно от полного onboarding, чтобы начать подготовку.
- Как администратор, я хочу видеть перечень базовых ролей, чтобы понимать будущую модель доступа.

## 4.6. Acceptance criteria фазы

Фаза считается завершённой, если:

1. Можно создать заказчика вручную через API.
2. Можно получить список клиентов и карточку клиента.
3. Можно получить список шаблонов и preview структуры шаблона.
4. Все endpoint'ы возвращают единообразный JSON-контракт.
5. Ошибки по валидации возвращаются в стандартном формате.
6. Seed-данные ролей и шаблонов разворачиваются предсказуемо.
7. Frontend может отобразить клиентов и шаблоны без ручных временных адаптеров.

## 4.7. Риски фазы

- слишком рано начать делать сложную RBAC-модель;
- перегрузить шаблоны лишними деталями;
- смешать справочники MVP и production-grade configuration management.

## 4.8. Что не делать в этой фазе

- не строить полноценную auth-подсистему enterprise-уровня;
- не делать сложный редактор шаблонов;
- не делать orchestration;
- не делать массовый импорт.

# 5. Phase 2 — Org Structure & Workforce Core

## 5.1. Цель фазы

Построить основные операционные сущности предприятия:

- оргструктуру;
- должности;
- сотрудников.

Результат фазы:

- можно развернуть структуру предприятия вручную;
- можно создать подразделения и секции;
- можно создать должности и сотрудников;
- можно связать сотрудников с подразделениями и должностями.

## 5.2. Почему это отдельная фаза

Даже без one-click onboarding проект уже начинает приносить практическую пользу, если можно вручную завести целевую структуру предприятия. Кроме того, именно здесь стабилизируются самые важные связи данных, от которых потом зависит bootstrap.

## 5.3. Scope фазы

### Backend

Реализовать:

- `GET /api/v1/org-units`
- `GET /api/v1/org-units/tree`
- `POST /api/v1/org-units`
- `PATCH /api/v1/org-units/{org_unit_id}`
- `POST /api/v1/org-units/bulk`
- `GET /api/v1/positions`
- `POST /api/v1/positions`
- `PATCH /api/v1/positions/{position_id}`
- `POST /api/v1/positions/bulk`
- `GET /api/v1/employees`
- `POST /api/v1/employees`
- `GET /api/v1/employees/{employee_id}`
- `PATCH /api/v1/employees/{employee_id}`
- `POST /api/v1/employees/bulk`

Подготовить:

- правила ссылочной целостности;
- валидации кодов оргединиц и должностей;
- защиту от циклов в дереве оргструктуры.

### Database / Model

Создать таблицы:

- `org_units`
- `positions`
- `employees`

Обеспечить связи:

- `org_units.client_id -> clients.id`
- `positions.client_id -> clients.id`
- `positions.org_unit_id -> org_units.id`
- `employees.client_id -> clients.id`
- `employees.org_unit_id -> org_units.id`
- `employees.position_id -> positions.id`

### Frontend

Реализовать минимальные экраны:

- просмотр дерева оргструктуры;
- создание и редактирование оргединиц;
- список должностей;
- форма создания должности;
- список сотрудников;
- форма создания сотрудника;
- карточка сотрудника.

### UX

На этом этапе важно сделать не «красивый мастер», а **надёжные формы ручного ввода**, потому что именно они станут контрольным каналом для проверки модели данных.

## 5.4. Endpoint coverage фазы

Фаза закрывает следующие endpoint'ы:

- `GET /api/v1/org-units`
- `GET /api/v1/org-units/tree`
- `POST /api/v1/org-units`
- `PATCH /api/v1/org-units/{org_unit_id}`
- `POST /api/v1/org-units/bulk`
- `GET /api/v1/positions`
- `POST /api/v1/positions`
- `PATCH /api/v1/positions/{position_id}`
- `POST /api/v1/positions/bulk`
- `GET /api/v1/employees`
- `POST /api/v1/employees`
- `GET /api/v1/employees/{employee_id}`
- `PATCH /api/v1/employees/{employee_id}`
- `POST /api/v1/employees/bulk`

## 5.5. Основные user stories фазы

- Как администратор внедрения, я хочу вручную собрать оргструктуру предприятия, чтобы подготовить её к запуску.
- Как оператор, я хочу создавать должности внутри подразделений, чтобы формировать штатную модель.
- Как оператор, я хочу создавать сотрудников и привязывать их к должностям, чтобы подготовить кадровую структуру клиента.

## 5.6. Acceptance criteria фазы

Фаза считается завершённой, если:

1. Можно создать минимум трёхуровневую оргструктуру без нарушения дерева.
2. Можно получить дерево оргструктуры клиента через один endpoint.
3. Можно создать должность внутри подразделения.
4. Можно создать сотрудника и привязать его к подразделению и должности.
5. Bulk-операции работают хотя бы для оргединиц, должностей и сотрудников.
6. Некорректные ссылки на несуществующие подразделения и должности блокируются.
7. Frontend отображает структуру и связанные справочники без ручной коррекции payload.

## 5.7. Риски фазы

- неверно определить границы уникальности кодов;
- не продумать parent/child-валидации;
- попытаться сразу строить слишком сложную модель ставок, совместительства и кадровых переводов.

## 5.8. Что не делать в этой фазе

- не уходить в HRIS-полноту;
- не строить сложную историю кадровых движений;
- не добавлять расчёт зарплаты, KPI и performance-логику.

# 6. Phase 3 — Accounts, Roles & Access Readiness

## 6.1. Цель фазы

Подготовить минимальный контур доступа:

- аккаунты;
- роли;
- связь аккаунта с сотрудником;
- статус доступности пользователя для входа.

Результат фазы:

- сотруднику можно создать аккаунт;
- аккаунту можно назначить базовые роли;
- есть минимальная готовность к реальному доступу в систему;
- orchestration в следующей фазе сможет создавать учётные записи автоматически.

## 6.2. Почему это не Phase 1

Потому что для MVP важнее сначала стабилизировать бизнес-сущности предприятия. Аккаунты без сотрудников и оргструктуры мало что дают, а вот обратная последовательность логична.

## 6.3. Scope фазы

### Backend

Реализовать:

- `GET /api/v1/accounts`
- `POST /api/v1/accounts`
- `PATCH /api/v1/accounts/{account_id}`
- `POST /api/v1/accounts/bulk`
- опционально: `POST /api/v1/accounts/{account_id}/reset-password`

Уточнить:

- как хранится login;
- создаётся ли temporary password;
- как назначаются `role_codes`;
- допускается ли несколько ролей;
- что считается статусом аккаунта.

### Database / Model

Создать таблицы:

- `accounts`
- `account_roles` или эквивалент many-to-many

Минимальные поля аккаунта:

- id
- employee_id
- login
- password_hash или эквивалент
- status
- created_at
- updated_at

### Frontend

Реализовать:

- список аккаунтов клиента;
- форму создания аккаунта для сотрудника;
- редактирование статуса аккаунта;
- назначение ролей.

### Security / Auth readiness

На MVP-уровне достаточно определить:

- как будет происходить начальная выдача доступа;
- что такое активный и неактивный аккаунт;
- как будут храниться временные пароли или invite-механизм.

Полный enterprise IAM в этой фазе не нужен.

## 6.4. Endpoint coverage фазы

Фаза закрывает следующие endpoint'ы:

- `GET /api/v1/accounts`
- `POST /api/v1/accounts`
- `PATCH /api/v1/accounts/{account_id}`
- `POST /api/v1/accounts/bulk`
- `POST /api/v1/accounts/{account_id}/reset-password` — если оставляем в MVP

## 6.5. Основные user stories фазы

- Как администратор клиента, я хочу создать аккаунт сотруднику, чтобы он мог работать в системе.
- Как администратор, я хочу назначить пользователю базовую роль, чтобы определить его место в системе.
- Как оператор внедрения, я хочу видеть, у каких сотрудников уже есть аккаунты, а у каких нет.

## 6.6. Acceptance criteria фазы

Фаза считается завершённой, если:

1. Можно создать аккаунт для существующего сотрудника.
2. Нельзя создать аккаунт для несуществующего сотрудника.
3. Можно назначить аккаунту одну или несколько ролей из разрешённого словаря.
4. Можно получить список аккаунтов клиента.
5. Можно изменить статус аккаунта.
6. Bulk-создание аккаунтов работает для onboarding-потока.
7. Есть минимальная модель, совместимая с будущей аутентификацией.

## 6.7. Риски фазы

- преждевременная перегрузка security-логики;
- смешение роли сотрудника в оргструктуре и системной роли доступа;
- неявные правила уникальности login/email.

## 6.8. Что не делать в этой фазе

- не строить SSO;
- не делать сложное self-service управление доступом;
- не строить тонкие permission matrix на каждую кнопку UI.

# 7. Phase 4 — One-click Onboarding Orchestration

## 7.1. Цель фазы

Собрать все уже реализованные части в единый сценарий one-click onboarding.

Результат фазы:

- мастер-запрос создаёт заказчика, оргструктуру, должности, сотрудников, аккаунты и роли;
- система отслеживает статус выполнения run;
- поддерживается dry-run;
- поддерживается идемпотентность запроса.

Это ключевая фаза MVP, потому что именно она превращает набор разрозненных CRUD в реальный продуктовый сценарий.

## 7.2. Scope фазы

### Backend orchestration

Реализовать:

- `POST /api/v1/bootstrap/enterprise`
- `GET /api/v1/onboarding-runs`
- `GET /api/v1/onboarding-runs/{run_id}`
- `GET /api/v1/onboarding-runs/{run_id}/steps`

Поддержать:

- request-level validation;
- dry-run mode;
- step-by-step execution;
- error capture per step;
- run status transitions;
- idempotency key / request_id;
- безопасную обработку частично завершённых запусков.

### Orchestration design

На уровне application service желательно выделить отдельный orchestration-компонент, например:

- `EnterpriseBootstrapService`
- `OnboardingRunService`
- `OnboardingValidationService`

Минимальные шаги run:

1. validate_request
2. create_or_get_client
3. resolve_template
4. create_org_units
5. create_positions
6. create_employees
7. create_accounts
8. assign_roles
9. finalize_run

### Database / Model

Создать таблицы:

- `onboarding_runs`
- `onboarding_run_steps`
- возможно, `idempotency_registry` или эквивалент

Минимальные поля run:

- run_id
- request_id
- client_id
- status
- current_step
- progress
- payload_hash
- started_at
- finished_at
- error_message

### Frontend

На этом этапе можно сделать ещё не wizard, а **экран запуска orchestration через structured form или JSON-assisted form**.

Минимум нужен:

- экран запуска onboarding;
- экран статуса run;
- экран детализации шагов run;
- индикация dry-run результата.

## 7.3. Endpoint coverage фазы

Фаза закрывает следующие endpoint'ы:

- `POST /api/v1/bootstrap/enterprise`
- `GET /api/v1/onboarding-runs`
- `GET /api/v1/onboarding-runs/{run_id}`
- `GET /api/v1/onboarding-runs/{run_id}/steps`

## 7.4. Основные user stories фазы

- Как оператор внедрения, я хочу одним запуском развернуть базовую структуру предприятия, чтобы сократить рутинную настройку.
- Как оператор, я хочу сначала выполнить dry-run, чтобы увидеть ошибки до фактического создания сущностей.
- Как администратор, я хочу видеть прогресс и ошибки выполнения onboarding, чтобы контролировать внедрение.

## 7.5. Acceptance criteria фазы

Фаза считается завершённой, если:

1. Один запрос может создать предприятие end-to-end в пределах MVP-модели.
2. Повторный identical request не создаёт дубликатов.
3. Dry-run корректно валидирует payload и не пишет данные в БД.
4. Статус выполнения run можно получить отдельным endpoint.
5. Шаги выполнения run доступны отдельно.
6. При ошибке run завершён прозрачно, с фиксированным статусом и сообщением.
7. Частично успешный сценарий либо корректно маркируется, либо откатывается по заранее выбранному правилу.

## 7.6. Критически важное архитектурное решение фазы

В этой фазе обязательно нужно выбрать один из двух подходов:

### Вариант A — best effort / partial completion

Система создаёт сущности по шагам. При сбое фиксирует частично завершённый результат и статус `partially_completed`.

Плюсы:

- проще реализовать;
- удобнее для длинных сценариев;
- лучше подходит для дальнейшего resume.

Минусы:

- требует аккуратной повторной обработки;
- усложняет cleanup.

### Вариант B — transaction-heavy rollback model

При ошибке система откатывает всё назад.

Плюсы:

- кажется чище на уровне бизнес-ожиданий.

Минусы:

- сильно усложняет реализацию;
- хуже работает на длинных многошаговых операциях;
- труднее масштабируется на внешние интеграции.

Для MVP рекомендуется **Вариант A: partial completion + прозрачные статусы**, потому что он практически реалистичнее.

## 7.7. Риски фазы

- попытка сделать orchestration «слишком умным»;
- отсутствие ясного правила идемпотентности;
- смешение бизнес-валидации и исполнения в одном неуправляемом блоке;
- слабая наблюдаемость шагов run.

## 7.8. Что не делать в этой фазе

- не подключать внешние системы до стабилизации ядра;
- не строить распределённую сагу enterprise-уровня;
- не делать сложный engine для кастомных сценариев.

# 8. Phase 5 — UI Wizard, Polish & MVP Hardening

## 8.1. Цель фазы

Сделать продукт пригодным для реального использования операторами внедрения, а не только для технического тестирования API.

Результат фазы:

- есть полноценный UI-мастер one-click onboarding;
- пользователь идёт по шагам, а не собирает payload вручную;
- ошибки и валидации отображаются понятно;
- есть минимальный UX polish и техническое укрепление MVP.

## 8.2. Scope фазы

### Frontend

Реализовать мастер из шагов:

1. выбор шаблона;
2. ввод данных клиента;
3. просмотр / корректировка оргструктуры;
4. просмотр / корректировка должностей;
5. ввод сотрудников;
6. правила создания аккаунтов;
7. экран подтверждения;
8. запуск dry-run или actual run;
9. экран прогресса и результата.

Обязательно поддержать:

- сохранение текущего состояния формы в памяти или черновике;
- отображение field-level validation;
- user-friendly тексты ошибок;
- предотвращение случайного повторного запуска;
- показ статуса завершения и списка созданных сущностей.

### Backend hardening

Доработать:

- более полные validation messages;
- traceability run-to-entities;
- улучшенные run logs;
- базовые ограничения на повторные вызовы;
- защиту от кривых payload на boundary API.

### QA / Testing

Подготовить:

- smoke tests по фазам;
- интеграционные тесты onboarding;
- тесты dry-run;
- тесты идемпотентности;
- тесты ошибок по несогласованным ссылкам.

## 8.3. Endpoint coverage фазы

Новые endpoint'ы в этой фазе могут не добавляться. Главный смысл фазы — довести уже реализованный API и UI до уровня пригодности для MVP-демонстрации и пилотного использования.

## 8.4. Основные user stories фазы

- Как оператор внедрения, я хочу пройти onboarding через понятный мастер, а не через ручную сборку JSON.
- Как пользователь бизнеса, я хочу видеть, что именно будет создано, до запуска.
- Как администратор, я хочу быстро понять, на каком шаге произошла ошибка и что нужно исправить.

## 8.5. Acceptance criteria фазы

Фаза считается завершённой, если:

1. Пользователь может пройти весь сценарий onboarding через UI без прямого обращения к API.
2. Dry-run доступен из UI.
3. Ошибки валидации отображаются на соответствующих шагах мастера.
4. После запуска пользователь видит прогресс выполнения и финальный статус.
5. Повторный запуск с теми же данными не приводит к хаосу и дублям.
6. Есть минимальный пакет smoke/integration тестов.
7. MVP можно показать стейкхолдерам как связный продуктовый сценарий.

## 8.6. Риски фазы

- слишком рано уйти в визуальный polish вместо стабильности;
- перегрузить wizard сложной настройкой;
- попытаться поддержать все нестандартные случаи до стабилизации базового happy path.

## 8.7. Что не делать в этой фазе

- не превращать мастер в универсальный конструктор всего предприятия;
- не добавлять лишние интеграции только ради демонстрационной полноты;
- не размазывать MVP hardening в бесконечный этап «ещё чуть-чуть улучшить».

# 12. Что считать первым реально демонстрируемым MVP

Практически MVP можно считать состоявшимся, если выполнены следующие условия:

1. Есть шаблон предприятия.
2. Есть форма или мастер создания нового клиента.
3. Есть возможность создать оргструктуру, должности и сотрудников.
4. Есть возможность создать аккаунты и назначить роли.
5. Есть one-click onboarding endpoint.
6. Есть dry-run.
7. Есть экран или экранный сценарий, показывающий статус run.

Это уже достаточно, чтобы:

- показывать продукт заказчику;
- тестировать реальный сценарий внедрения;
- собирать обратную связь;
- переходить к расширению платформы.
